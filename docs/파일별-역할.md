# 파일별 역할

> 파일마다 가장 중요한 결정을 **중요한 결정** 줄에 모았다. 코드에는 그 자리에 왜 그렇게 했는지만 한 줄 주석으로 적었다.
> JSON은 주석을 달 수 없어 파일 첫 필드에 `_역할` 또는 `note`로 남겼다.

## `core/verdict.py` — 판정 코드

| | |
| --- | --- |
| **역할** | 일정이 실행 가능한지 판정한다. 이 프로젝트의 중심 |
| **입력** | `judge(itinerary, facts, policy)` — 셋 다 **인자로** 받는다 |
| **출력** | `checks[]` · `hard_constraints[]` · `assumptions[]` · `summary` |
| **의존** | 없음. 표준 라이브러리만 쓴다 |

**네트워크를 부르지 않는 것이 규칙이다.** 이 파일에 API 호출이 한 줄 들어가는 순간 고정 입력으로 테스트할 수 없게 된다. 그래서 사실과 우리 기준을 전부 인자로 받는다.

**검사 종류**

| 코드 | 무엇을 보나 | 필요한 근거 |
| --- | --- | --- |
| `INPUT_REQUIRED` | **판정에 필요한 입력이 있나** | 없음. 입력만 본다 |
| `INPUT_CONFLICT` | **입력끼리 맞나** — 말한 요일이 날짜와 다르면 어느 날인지 묻는다 | 없음. 입력만 본다 |
| `CLOSED_DAY` | 방문일이 휴무일인가 | 정기휴일 + 공휴일 캘린더 + 기관별 예외 규칙 |
| `ADMISSION_NOT_POSSIBLE` | 도착 시각에 **입장**할 수 있나. 개장 전 도착은 기다려서 개장 시각에 들어간다고 본다 | 운영시간 + 입장마감 |
| `DWELL_NOT_COMPLETABLE` | 계획한 **체류를 마칠** 수 있나 | 위 + 체류시간 |
| `INSUFFICIENT_TRAVEL_TIME` | 다음 장소에 제때 가나 | 구간 이동시간 + 앞 장소 종료 시각 |

`INPUT_REQUIRED`가 나머지 넷보다 먼저 돈다. 구조화 추출 단계가 날짜나 시작 시각을 `None`으로
남기는 일이 있는데, 그 값을 시간 계산에 그대로 넘기면 프로그램이 예외로 죽는다.
**입력이 부족한 것도 검증 결과의 일부**이므로 죽지 않고 미확인으로 낸다. **입력이 일부 빠져도 확인할 수 있는 검사는
계속한다** — 날짜가 없거나 읽을 수 없거나 장소가 하나도 없을 때만 판정 전에 묻는다(`WHOLE_ITINERARY_INPUTS`). 장소 하나의
이름 · 시각이 빠지면 그 장소와 앞뒤 구간만 미확인이고, 다른 장소의 위반은 그대로 전체 판정에 들어간다(3차 피드백 —
시각 없는 덕수궁 하나 때문에 2026-01-01 미술관 휴관 위반이 사라졌다).

**함수** — `judge()`가 일곱 단계를 차례로 부르고, 큰 검사는 '미리 결론이 나는 경우를 거르는 함수'와 '데이터로 판정하는
함수'로 나눠 두었다. 함수마다 한글 설명이 붙어 있다. 파일을 위에서부터 읽으면 단계 순서대로 나온다.

| 함수 | 하는 일 |
| --- | --- |
| `to_min` / `to_hhmm` | 시각을 분 단위 정수로 다룬다. 시간 계산 버그를 줄이기 위한 것 |
| `weekday_of` / `shift_date` | 요일 계산, 날짜 이동 |
| `evidence_usable_on` | 근거의 **적용 기간** 검사. 방문일이 `valid_until`을 넘으면 그 근거는 못 쓴다 |
| `check` | 검사 결과 dict 생성. 위반일 때만 심각도(`severity`)를 붙인다 |
| `input_checks` | **판정 전에 입력이 성립하는지 본다.** 날짜·장소·시각이 비었으면 예외를 내지 않고 미확인 검사로 돌려준다 |
| `closed_date_for` | 그 주의 실제 휴무일 계산. **기관별 예외 규칙을 facts에서 읽어 분기** |
| `check_closed_day` | 휴무일 검사. 근거를 쓸 수 없으면(`_closed_day_unusable`) 미확인, 고정 휴관일은 `_fixed_date_closure`가 본다 |
| `hours_for` | 그 날짜에 적용되는 시간표 선택. **공휴일 시간표가 요일보다 우선** |
| `check_admission` | 입장 가능 검사. 시간표 없이 결론이 나는 회차 입장·상시 개방·공휴일 캘린더는 `_admission_without_hours`, 시간표 판정은 `_admission_by_hours`. 개장 전 도착은 안내(`notice`)를 붙이고 입장 시각(`entry_at`)을 개장으로 늦춘다 |
| `check_dwell` | 체류 완료 검사. 사용자가 체류시간을 안 말했으면 판단하지 않는다 |
| `leg_between` | `"A\|B"` 키로 구간 조회 |
| `support_scope` | 장소를 셋으로 나눈다 — 정보가 있는 장소 · 지원 목록 밖 · 동네. 구조화 추출 채점도 같은 함수를 쓴다 |
| `check_travel` | 이동시간 검사. 이동 0분으로도 늦는지(`_late_without_travel`), 판정할 수 없는 구간 — 동네 · 구간 없음 · 근거 기간 밖(`_leg_unusable`), 이동시간 판정(`_travel_by_leg`) 순서다. 최소 이동시간은 한 방향으로만 말해 줌, 최소 체류 0분, 되는 수단이 하나라도 있으면 통과(이동수단은 보지 않음), 예상 이동시간 · 지하철 최소 이동시간으로는 위반 확정 안 함(`_late_travel`), 대중교통으로 안 되면 택시 대안 |
| `evaluate_hard_constraint` | KTX 같은 필수 일정. `event`(사용자)와 `policy`(우리 기준)를 분리한다. 우리 기준 평가(`_hc_policy`)는 이동 검사와 같은 순서이고, 시각의 뜻(출발 시각이면 그 시각에 닿아도 놓친 것)은 `_Deadline`이 들고 있다. 권장 여유 기준이 없으면(항공편) 통과를 내지 않는다 |
| `unconfirmed` | 추정한 입력에 기대는 통과 · 위반을 미확인으로 내리고, 계산 결과는 참고로 남긴다 |
| `judge` | 본체. 입력 확인 → 날짜 · 요일 → 장소 준비(`_prepare_stop`, 추정 시각 · 기본 체류시간을 `assumptions`에 기록) → 장소 검사(`_place_checks`) → 구간 검사(`_travel_checks`) → 필수 일정(`_hard_constraints`) → 전체 판정(`_summary`) |

**보류 이유(`unknown_reason`) 종류** — 같은 미확인이라도 해결 방법이 다르므로 구분한다

| 이유 | 뜻 | 어떻게 해결하나 |
| --- | --- | --- |
| `NO_CLOSED_DAY_DATA` · `NO_OPERATING_HOURS_DATA` | 정보를 못 구했다 | 데이터 확보. 시장처럼 점포마다 다른 곳은 갈 점포를 묻는다 |
| `EVIDENCE_EXPIRED` | 근거의 적용 기간이 지났다 | 다시 확인 |
| `PLACE_NOT_RESOLVED` | 동네만 말해서 방문할 시설이나 가게를 특정하지 못했다 | 사용자에게 어디로 가는지 묻는다 |
| `UNSUPPORTED_PLACE` | 지원하는 장소 목록에 없어 확인하지 않았다 | 장소 정보를 확보한다. 사용자에게 묻지 않는다 |
| `HOLIDAY_CALENDAR_UNVERIFIED` | 공휴일 달력을 아직 확인하지 않았다 | API 호출 |
| `UNVERIFIED_TRAVEL_TIME` | 구간 이동시간이 없다 | 데이터 확보 |
| `LOWER_BOUND_ONLY` | 최소 이동시간밖에 없다 | 걷기·환승·대기 시간 확보 |
| `NO_USER_DWELL` | 사용자가 체류시간을 안 말했다 | 사용자에게 물어본다 |
| `LATE_BY_LOWER_BOUND` | 지하철 **최소 이동시간**으로도 늦는다. 지하철로는 못 가지만 택시 등 다른 수단은 확인하지 못했다 | 사용자에게 알리고 일정 조정을 묻는다 |
| `LATE_BY_ESTIMATE` | 길찾기 **예상 이동시간**으로는 늦는다. 예상치라 확정하지 않는다 | 사용자에게 알리고 일정 조정을 묻는다 |
| `INFERRED_INPUT` | LLM 이 **추정한 입력**(시각, 요일 없이 채운 연도)으로만 나온 결과다 | 사용자에게 확인한다 |
| `BUFFER_NOT_MET` | 열차 출발·다음 장소 시작 전에는 닿지만 **권장 여유에 못 미친다** | 사용자에게 알리고 판단을 맡긴다 |
| `NO_BUFFER_RULE` | 필수 일정에 둘 **권장 여유 기준이 없다** — 항공편 탑승 수속 · 보안 검색 | 사용자에게 알리고, 공식 안내를 확보한다 |
| `RULE_CONFLICT` | 공식 문구 두 개가 **반대 결론**을 낸다 (미술관 1월 1일이 월요일인 해) | 기관에 확인 |
| `MIDDAY_HARD_CONSTRAINT` | 필수 일정이 **하루 중간**에 있다(그 시각 이후에 시작하는 장소가 있다). 필수 일정은 아직 하루 마지막 교통편만 판정한다. 그 일정을 사이에 둔 두 장소의 이동도 같은 이유로 미확인이다 | 앞뒤 장소와 잇는 검사를 만든다. 그때까지는 사용자에게 알린다 |
| `DWELL_BEYOND_TOUR` | 회차 입장 날(종묘 월·목·금)에 말한 체류가 **해설 관람(50분 정도)보다 길다**. 일반관람이 안 돼 더 머물 수 있는지 공식 안내가 없다 | 사용자에게 해설 시간 안으로 잡아도 되는지 묻는다 |
| `AT_LAST_ADMISSION` | **입장마감 정각**에 도착한다. 공식 안내가 시각만 적어 정각에 들어가는지 말하지 않는다(궁궐) | 사용자에게 조금 일찍 도착할 수 있는지 묻는다 |
| `UNVERIFIED_ALWAYS_OPEN` | 상시 개방이라는 공식 근거를 확보하지 않았다 | 공식 출처 확인 |

입력이 부족하거나 서로 맞지 않아서 나는 것은 따로 묶는다. 전부 사용자에게 되물어 해결한다.

| 이유 | 뜻 |
| --- | --- |
| `MISSING_DATE` · `INVALID_DATE` | 방문 날짜가 없거나 `YYYY-MM-DD`로 못 읽는다 |
| `MISSING_STOPS` · `MISSING_PLACE` | 방문할 장소가 없다 |
| `MISSING_START_TIME` | 방문 시작 시각이 없다. 그 장소의 휴무일은 날짜로 확인하고, 입장 · 체류와 앞뒤 이동을 이 이유로 묻는다 |
| `INVALID_TIME` | 시각을 `HH:MM`(24시간)으로 못 읽는다 — `"1:00 PM"` 같은 값 |
| `INCOMPLETE_HARD_CONSTRAINT` | 필수 일정에 장소 또는 시각이 빠졌다. 필수 일정은 결과에 그대로 남긴다 |
| `MISMATCHED_WEEKDAY` | 날짜와 요일이 서로 맞지 않는다. 어느 날을 뜻했는지 모르므로 불가능이 아니라 보류다 |

> `BUFFER_NOT_MET`이 위반이 아니라 미확인인 이유 — 사용자가 반드시 지켜야 하는 것은
> **열차 출발 시각**과 **다음 장소 시작 시각**이다. 열차 15분 전 도착, 구간 이동 10분 여유는
> 우리가 정한 권장 기준이지 사용자 일정의 확정 위반이 아니다. 그 시각 자체를 넘기면 그때
> 위반이 된다. 권장 여유를 위반에 섞으면 설정값을 올리기만 해도 가능한 일정이 불가능이 된다.

**중요한 결정** — 4상태 · 개장 전 도착은 불가능이 아님 · 추정 입력은 확정하지 않음 · 근거 적용기간 · 기관별 예외 · 고정일 휴관과 규칙 충돌 · 공휴일 시간표 우선 · '해당 없음'도 근거 필요 · 보류 이유 구분 · 입장/체류 분리 · 대중교통으로 안 되면 택시 대안 · 이동 0분으로도 늦을 때만 위반 · 이동수단은 보지 않음 — 되는 수단이 하나라도 있으면 통과 · 예상치로는 위반 확정 안 함 · 최소 체류 0분 · 최소 이동시간은 한 방향으로만 · 권장 여유는 위반에 쓰지 않음 · 기준 없는 필수 일정은 통과 안 냄 · 사용자 조건과 우리 기준 분리 · 검사 상태 ≠ 심각도 · **입력 결손은 예외가 아니라 미확인** · **동네 일정을 대표 시설로 바꿔 판정하지 않음** · 지원 목록 밖 장소와 동네는 푸는 쪽이 다름 · 시장만 점포를 물음 · 기본값 기록 · 전체 판정 · 사용자 문구

## `core/recheck.py` — 수정 후 전체 일정 재검사

`recheck_revision(original, revised, facts, policy)`는 수정 전과 수정 후에
각각 `judge()`를 호출한다. 바뀐 장소만 다시 보는 것이 아니라 날짜·장소·체류시간·이동시간·필수 일정을 포함한 수정 일정 전체를 재검사하고, 바뀐 칸의 경로를 함께 남긴다.

고친 일정이 사용자가 꼭 지킨다고 한 것을 바꿨으면 `needs_confirmation`에 따로 적는다. 판정이 나아진 것만으로 수정을 받아들이지 않기 위해서다 — 장소를 지우면 확인할 것이 줄어 판정이 나아지고, 날짜를 옮기면 예약한 열차도 새 날짜에 탈 수 있는 것처럼 판정된다.

| 종류 | 언제 |
| --- | --- |
| `DATE_MOVED` | 필수 일정(열차 등)이 있는데 날짜가 다른 날로 바뀌었다. 날짜를 처음 채우거나 지운 것은 옮긴 것이 아니다 |
| `HARD_CONSTRAINT_CHANGED` | 필수 일정의 종류·장소·시각이 바뀌었거나 빠졌다 |
| `STOP_DROPPED` | 원래 장소가 고친 일정에 없다 — 빠졌거나 다른 장소로 바뀌었다 |

시각 · 체류시간 · 방문 순서는 고쳐도 되는 것이라 적지 않는다. 장소는 순서가 아니라 이름으로 짝을 맞춘다. 순서로 비교하면 방문 순서만 바꿔도 장소가 바뀐 것처럼 보인다.

`revised_facts`를 넘기면 고친 일정만 그 사실로 판정한다. 데모(`core/app.py`)는 고친 출발 시각으로 이동시간을 새로 받아
여기에 넣고, 원래 일정은 처음 검사에서 받은 이동시간으로 다시 본다. 둘을 섞으면 같은 구간을 다른 시각의 값으로
판정해서 '수정 전' 판정이 처음 화면에서 본 것과 달라질 수 있다.

**중요한 결정** — 판정이 나아진 것만으로 수정을 받아들이지 않음 · 장소는 이름으로 짝을 맞춤

## `core/report.py` — 결과 묶기

| | |
| --- | --- |
| **역할** | 판정 결과를 사용자에게 보여줄 묶음으로 나눈다 |
| **입력** | `report(result)` — `judge()`의 결과. **읽기만 하고 바꾸지 않는다** |
| **출력** | `groups[]` — 어긋난 것 · 확인하지 못한 것 · 확인한 것 · 해당 없음 / `not_checked[]` — 검사하지 않는 것 / `questions(result)` — 물을 말을 한 번씩만 / `timeline(itinerary, result)` — 일정 순서의 줄(장소 · 이동 · 필수 일정)과 줄마다 가장 나쁜 상태 |
| **읽는 쪽** | `run.py` · `verify.py` — `render()`로 `[결과]`를 찍는다 / `app.py` — 화면에 묶음 · `questions()` · `timeline()`을 보낸다 |

멘토 피드백 2번 — 결과 화면에서도 검사한 것과 확인하지 못한 것을 각각 보여줘야 한다. 묶는 방식은 웹 접근성 검사기 axe-core(위반 · 통과 · 판단 못 함 · 해당 없음)와 Lighthouse(도구가 검사하지 않는 항목을 매 보고서에 붙인다)를 따랐다. 고칠 것이 먼저 보이도록 어긋난 것부터 적는다.

**검사하지 않는 것을 결과마다 붙인다.** '가능'은 "이 목록을 뺀 범위에서 위반을 찾지 못했다"는 뜻이기 때문이다. 목록은 이 파일 한 곳에 있고, [지원 범위](../README.md#지원-범위) 표의 '검사하지 않는 것' 칸과 글자까지 같은지 `tests/test_report.py`가 대조한다.

**같은 것을 여러 검사가 물어도 한 번만 묻는다(`questions()`).** T12는 경복궁 체류시간을 몰라 체류 검사는 "얼마나
머무르실", 다음 구간은 "몇 시에 나오실"로 묻고, 광장시장 휴무일과 입장이 똑같이 점포를 묻는다. 질문은 넷인데 답할
것은 둘이다. 판정이 기댄 가정(체류시간 기본값, 추정한 날짜와 시각)이 있으면 그 가정의 질문으로 묻고, 장소 이름이 없는
질문에는 장소를 붙인다. 데모 화면이 쓰고, CLI의 `[결과]`는 항목마다 질문을 그대로 둔다.

**화면은 일정 순서로 보여 준다(`timeline()`).** 상태별 묶음만 있으면 장소가 네다섯 곳일 때 어느 장소가 문제인지 일정과
다시 맞춰 봐야 한다(2026-10-14 사용자 제안). 장소마다 한 줄, 장소 사이 이동 한 줄, 끝에 필수 일정이고, 줄의 표시는 그 줄
검사 중 가장 나쁜 것이다. 미확인(?)은 통과(✓)로도 위반(✗)으로도 보이지 않게 따로 둔다 — 1차 피드백의 첫 지적이 그 구분이다.
상태별 묶음과 검사마다의 근거는 그 아래 '상태별로 보기'에 접어 둔다. 정답 문제 33건 전부에서 검사가 한 줄에 한 번씩만
들어가는지 `tests/test_report.py`가 본다.

**중요한 결정** — 해당 없음도 이유와 함께 보여줌 · 검사하지 않는 것을 결과마다 붙임

## `core/extract.py` — 자연어 일정의 구조화 추출

| | |
| --- | --- |
| **역할** | 자연어 일정에서 날짜 · 장소 · 시각을 뽑아 판정 코드가 읽는 구조로 만든다(**구조화 추출**) |
| **입력** | `extract(text, client, model, today=…, effort)` — 기준 날짜 `today`는 꼭 넣는다. 함수 안에서 시스템 시계를 읽지 않는다 |
| **출력** | `(Extraction, usage)` → `to_itinerary()`로 판정 코드 입력 형태로 |
| **모델** | 기본 `claude-opus-5-5`(`core/model_info.py`), structured outputs (pydantic 스키마, 호출은 `core/llm.py`), `effort: low` |

**LLM이 담당하는 유일한 단계다.** 판정은 시키지 않는다. 자연어를 구조로 바꾸는 데는 강하지만 규칙을 일관되게 적용하는 데는 약하기 때문이다 (비교 실험 참조 — 놓치는 규칙이 실행마다 바뀌었다).

**pydantic 모델**

| 모델 | 필드 | 요점 |
| --- | --- | --- |
| `Stop` | `raw` `place` `start` `start_source` `dwell_minutes` `scope` `scope_note` `outside_only` | `dwell_minutes`가 **`int \| None`** 인 것이 핵심. `start`는 `HH:MM`(24시간), 체류는 1분\~24시간. `outside_only`는 입장하지 않고 밖에서만 머문다고 했는지(화면의 '입장 안 함') — 그러면 휴무 · 입장 · 체류는 해당 없음 |
| `HardConstraint` | `raw` `type` `place` `time` `time_source` | `"꼭 타야 해요"` 처럼 사용자가 못 박은 조건만. `time`은 `HH:MM`이고 모르면 `null` — 조건은 남기고 시각을 묻는다. 추정한 시각은 `inferred` |
| `Extraction` | `date` `date_source` `weekday_stated` `stops` `hard_constraints` `avoid_taxi` `notes` | `date`는 실제로 있는 날짜, `weekday_stated`는 `MON`\~`SUN`. 요일이 날짜와 맞는지는 판정 단계가 본다 |

`start_source`가 `explicit` / `inferred` / `missing` 셋인 이유 — `"점심 먹고"`를 12:00으로 읽은 것은 추정이고, `"오후 1시"`는 명시다. 기댈 앞 시각 없이 `"4시"`라고만 한 것도 추정이다(tests.json 절의 오전·오후 기준). 그 구분이 없으면 나중에 무엇이 사용자 말인지 알 수 없다.

`scope`가 `place`와 `area` 둘인 이유 — 판정은 위치가 정해진 곳의 근거를 찾는다. 궁 · 시장 · 건물처럼 위치가 하나로
정해지는 곳은 그 안의 어느 가게인지 몰라도 `place`다. 광장시장은 입구로 위치가 정해져 이동시간을 셀 수 있고, 가게마다
다른 영업시간은 판정 단계가 묻는다. 명동 · 북촌처럼 여러 골목에 걸친 동네는 `area`라 대표 지점으로 판정하지 않는다.

**받자마자 형식을 검증한다** (2차 피드백 4번) — 판정 코드가 읽을 수 없는 값(`"1:00 PM"`, `"2026-02-30"`)은 넘기지 않는다. 날짜 형식과 요일 목록은 스키마에 넣어 API가 지키게 하고, 시각 패턴과 체류 범위는 API가 설명으로만 받으므로 받은 뒤에 pydantic이 다시 본다. 값과 출처도 맞아야 한다 — 시각이 있는데 `start_source`가 `missing`이거나 날짜가 없는데 `date_source`가 `inferred`면 받지 않는다. 검증에 실패하면 `llm.InvalidOutput`이 난다.

**시스템 프롬프트 규칙 7개** — 없는 값을 만들지 않는다 / 추정은 표시한다 / 장소명을 고치지 않는다 / 동네(여러 골목에 걸친 곳)는 `area`로 남긴다 / 필수 일정은 `stops`에 중복하지 않는다 / 연도는 가장 가까운 미래로 / 요일은 옮기기만 한다

`effort: low`를 쓰는 이유 — 구조화 추출은 기계적인 작업이라 깊게 생각할 게 없다. 출력 토큰이 절반으로 줄었는데 정확도는 같았다.

**중요한 결정** — `int | None` · `scope: area` · LLM 경계 · 받자마자 형식 검증

## `core/facts.json` — 사실

| | |
| --- | --- |
| **역할** | 판정에 쓰는 **사실**. 운영정보·이동시간·공휴일 |
| **읽는 쪽** | `verdict.py` · `run.py` · `compare.py` |
| **쓰는 쪽** | 사람(공식 페이지에서 옮김, `curated`) · `build_transit_legs.py --write` · `fetch_holidays.py`(`holidays`) |

**최상위 구조**

| 키 | 내용 |
| --- | --- |
| `snapshot_id` | `facts-2026-09-29`. **데이터 버전.** 재확인이 필요한 정답을 찾을 때 이걸 읽는다 |
| `snapshot_history` | 버전별로 무엇이 바뀌었는지. `changed_keys`가 재확인 필요 판단의 근거 |
| `holidays` | `verified` · `dates[]` · 출처 · 적용기간 |
| `places` | 장소별 `closed_days` · `hours` · `admission`. 좌표는 두지 않는다 — 판정할 때 TMAP 장소 검색으로 받는다 |
| `legs` | 구간별 이동시간. `"A\|B"` 키 |
| `transit_source` | 지하철 데이터 출처와 라이선스 |

**값마다 붙는 근거 필드**

| 필드 | 왜 필요한가 |
| --- | --- |
| `source` | 공식 페이지에서 옮김(`curated`) / 공공데이터(`public_data`). **저장해 둘 수 있는 출처인지 판단하는 근거.** 판정할 때 받는 TMAP 구간은 TMAP 실시간 조회(`api_runtime`, 저장하지 않는다), 테스트가 정한 값은 테스트용 가상 값(`synthetic_fixture`) |
| `url` · `checked_at` | 어디서 언제 확인했나 |
| `valid_until` | **언제까지 쓸 수 있나.** 이게 없으면 작년 시간표로 올해를 판정한다 |
| `rule_text` | 공식 안내 문구 원문. 페이지가 바뀌었을 때 비교 기준 |
| `rule_scope` | 그 규칙이 어디까지 적용되나 |
| `verified_by` | 확인 방법 (`공식 페이지 화면 확인` 등) |

`place.admission.type`이 `timed_entry`면 회차 입장(종묘 평일), `always_open`이면 상시 개방 후보다. 후자는 `verified: false`인 동안 미확인으로 나온다.

`leg`의 `is_lower_bound: true`는 **도보·환승·대기가 빠진 최소 이동시간**이라는 표시다. `excluded[]`에 무엇이 빠졌는지 적혀 있다.

## `core/policy.json` — 우리 기준

| | |
| --- | --- |
| **역할** | 우리가 정한 **설정**. 기본값·권장 여유·판정 기준 |
| **읽는 쪽** | `verdict.py` · `compare.py` |

**파일 첫 줄에 이렇게 적어뒀다** — `"전부 우리가 정한 값이다. 출처 URL이 없다. 사실이 아니라 설정이다."`

`facts.json`과 분리한 이유가 이것이다. 사실과 설정을 한 파일에 두면 판정 결과를 보고 "이게 공식 정보인가 우리가 정한 값인가"를 구분할 수 없다.

| 키 | 값 | 뜻 |
| --- | --- | --- |
| `default_dwell_minutes` | palace 90 · museum 60 · market_meal 60 · street 45 | 체류시간 미입력 시 **안내에만** 쓰는 기본값. 판정에는 쓰지 않는다 |
| `buffer_minutes.transit_leg` | 10 | 구간 이동에 두는 여유 |
| `buffer_minutes.rail_boarding` | 15 | 열차 탑승 전 권장 도착 여유 |
| (`buffer_minutes.flight_boarding`) | 없음 | **일부러 두지 않는다.** 항공편은 탑승 수속 · 보안 검색 마감이 항공사 · 공항마다 달라 우리가 정한 값으로 '탈 수 있다'고 할 수 없다. 그래서 항공편은 통과가 나오지 않는다 |
| `require_user_dwell_for_completion_check` | true | 체류시간을 안 말했으면 체류 검사를 하지 않는다 |

첫 줄과 마지막 줄이 "우리가 정한 값으로 사용자 일정의 오류를 만들어내지 않는다"를 구현한 것이다. 9월 22일 비교 실험에서 LLM은 이 기준을 **문서로 받고도** 적용하지 않았다(T08).

## `core/tests.json` — 정답 문제와 정답

| | |
| --- | --- |
| **역할** | 정답 문제 35개와 정답 — 회귀셋 |
| **읽는 쪽** | `run.py` · `run_extract.py` · `compare.py` |

**새 평가는 `core/eval-new.json`에 따로 둔다(3차 피드백).** 같은 모양이고 `set`이 `new`다. 정답은 판정 코드를 돌리기 전에
사람이 공식 근거로 정해 먼저 커밋한다([워크시트](new-eval-worksheet.md)). 세 실행기에 `--suite eval-new.json`을 주면 돌고,
기록은 회귀셋 기록을 덮어쓰지 않게 이름을 붙여 따로 남는다(`last-run-eval-new.json` 등, `runmeta.record_name`).
처음 결과는 고치지 않고 남기고, 고친 문제는 `tests.json`으로 옮긴다.

**문제 하나에 들어가는 것**

| 필드 | 내용 |
| --- | --- |
| `id` · `set` | `T08-체류시간미입력` · `dev`(연습용) 또는 `holdout`(시험용) |
| `raw` | 입력 자연어 원문 |
| `date` · `date_source` · `weekday_stated` · `stops` · `hard_constraints` | **기대 추출값.** `run_extract.py`가 이것과 대조한다. `date_source`는 연도를 말했으면 `explicit`, 아니면 `inferred` |
| `expect_applied` | 적용해야 하는 사실·가정·빠진 정보 |
| `expect` · `expect_checks` · `expect_hard_constraints` | **기대 판정** |
| `why` | 왜 그 판정인지. 정답의 근거 |
| `label_review_needed` | 데이터가 바뀌어 재검토가 필요할 때 이유가 들어간다 |
| `legs` | (있을 때만) 문제별 이동시간. 테스트용 가상 값(`source: synthetic_fixture`)만 받는다 — 3\~6곳 일정을 고정값으로 채점하려고 정한 값이다 (`core/labels.py`의 `case_facts`) |
| `stops[].start_source` | (있을 때만) `inferred`면 추측한 시각이다. 아래 오전·오후 기준 |

**연습용과 시험용** — 연습용(`dev`)은 코드를 만들면서 계속 돌려 보고 고친 문제이고, 시험용(`holdout`)은 정답을 먼저
커밋하고 코드를 맞추지 않은 문제다.

**`labeled_against_snapshot`** — 이 정답을 어느 데이터 버전 기준으로 검토했는지. 문제마다 `labeled_against`로 덮어쓸 수 있다. 지금 `facts.json`의 데이터 버전(`snapshot_id`)과 다르다고 바로 무효로 보지 않는다. 정답을 검토한 버전 뒤의 데이터 변경(`snapshot_history`의 `changed_keys`)을 모두 보고, 그중 하나라도 그 문제가 쓰는 장소나 구간을 건드렸으면 재확인 필요로 본다(`core/labels.py`).

**`reference_date`** — 입력의 '오늘'. 연도가 빠진 날짜(`"10월 8일"`)는 이 날 기준 가장 가까운 미래로 푼다. 기대 추출값(`date`)이 이 날을 오늘로 보고 만들어졌다. `run_extract.py`와 `compare.py`가 읽고, 실행할 때 `--reference-date`로 바꿀 수 있다.

**오전·오후 기준** (2026-10-07) — 오전·오후·아침·저녁·밤 같은 말이 시각에 붙어 있거나 `17시 30분`처럼 24시간으로 말한
시각은 사용자가 말한 시각이다. 붙어 있지 않아도 같은 일정에서 앞에 나온 시각 뒤로 처음 오는 시각으로 정해지면 사용자가
말한 시각이다 — `오후 1시 … 3시`의 3시는 15:00이다. 기댈 앞 시각이 없을 때만(`5시 반에 경복궁`) 기대 추출값의
`start_source`를 `inferred`로 적고, 값은 일정에 가장 그럴듯한 쪽으로 적는다. 추측한 시각에 기대는 검사는 확정하지 않는다
([판정 규칙](판정-규칙.md)). 날짜·시각 파서 Chrono가 값마다 말한 것과 추측한 것을 나눠 두는 것(`isCertain`)과 같은 방식이다.
처음(10-06)에는 시각에 직접 붙은 말만 인정했는데, `오후 1시 … 3시`의 3시를 되묻는 것은 답이 뻔한 질문이라 첫 실행 전에 고쳤다.

> 정답은 판정 코드와 독립이어야 하지만 **데이터 버전과는 독립일 수 없다.**
> T10이 그 증거다 — 입력은 그대로인데 창덕궁 운영시간을 확보하자 정답이 바뀌었다.

## `core/run_extract.py` — 구조화 추출 채점 + 끝까지 돌리기

| | |
| --- | --- |
| **역할** | 자연어 → 구조화 추출 → 판정을 끝까지 돌리고 **구조화 추출과 판정을 따로 채점**한다 |
| **실행** | `python core/run_extract.py [--case T05,T22] [--extract-only] [--fresh] [--repeat 5] [--model ...] [--effort ...] [--reference-date ...]` — 새로 부를 호출이 있을 때만 키 필요 |
| **출력** | 화면 + `last-extract-run.json`. `--repeat`은 `last-extract-stability.json` |

모델에 보낼 내용이 같은 문제는 [응답 캐시](#coreresponse_cachepy--응답-캐시)에 받아 둔 응답을 쓴다. 채점과 판정은 그 응답을 가지고 지금 코드로 다시 한다.
새로 부를 호출이 있으면 건수와 예상 비용을 보여 주고 `y`를 받는다. 호출이 실패하면(잔액 부족 등) 공식 기록을 건드리지 않고 멈추고, 다시 돌리면 남은 것만 부른다.

두 단계를 따로 채점하는 이유 — 전체가 틀렸을 때 **구조화 추출 문제인지 판정 문제인지** 구분해야 고칠 곳을 알 수 있다.

**값만이 아니라 출처와 분류도 채점한다** (2차 피드백 3번). 연도를 사용자가 말했는지 추측했는지, 시각을 말했는지
추측했는지가 틀리면 판정이 물어야 할 것을 확정해 버린다. 지원 범위 분류는 판정 코드와 같은 함수(`verdict.support_scope`)로
기대값과 추출값을 각각 정보 있는 장소 · 목록 밖 · 동네로 나눠 비교한다. 요약에 항목별 점수가 따로 나온다.

**기준 날짜는 실행한 날이 아니라 `tests.json`의 `reference_date`다.** 실행한 날을 쓰면 날짜가 지날수록 같은 입력을 다른 연도로 옮겨서, 같은 조건으로 기록을 다시 만들 수 없다.

| 함수 | 하는 일 |
| --- | --- |
| `labels.grade_extraction` | 기대 추출값과 항목별로 대조한다 — 날짜·요일 · 연도 출처 · 장소 · 시각 · 시각 출처 · 체류시간 · 지원 범위 분류 · 필수 일정(시각 출처 포함) · 택시 안 탐. 테스트할 수 있게 `labels.py`에 둔다 |
| `ask_key` | `--key=` → 환경변수 → 물어보기 순서 |

비용 계산에 **캐시 토큰을 포함한다.** 이걸 빼면 실제보다 싸게 나온다. 캐시 단가는 모델마다 `core/model_info.py`에 값으로 적어 두었다 — 대부분 읽기가 입력의 0.1배지만 Opus 5.5는 0.05배다. 모델이 응답을 거부하거나(refusal) 형식에 맞지 않는 응답을 내면 그 문제는 오류로 남기고 계속 돈다. 거부된 호출은 청구되는 경우에만 비용에 넣는다(`core/model_info.py`).

1차 실행에서 구조화 추출 12/15였는데 실패 3건의 원인이 전부 **정답과 프롬프트 쪽**이었다. 입력에 없는 체류시간이 정답에 적혀 있었고, 필수 일정으로 뽑은 서울역이 `stops`에도 들어갔다. 모델이 틀린 건 0건이었다.

## `core/compare.py` — 비교 실험

| | |
| --- | --- |
| **역할** | 비교 방식 넷을 같은 문제로 돌려 비교한다 |
| **실행** | `python core/compare.py [--dry-run] [--fresh] [--repeat 5] [--arms ...] [--case T05,T27] [--model ...] [--effort ...] [--reference-date ...] [--key=...]` |
| **출력** | 화면 + `last-compare.json`. `--repeat`은 `last-compare-stability.json` |

LLM 방식 셋은 돈이 든다. 모델에 보낼 내용이 같은 요청은 [응답 캐시](#coreresponse_cachepy--응답-캐시)에 받아 둔 응답을 쓰고, 판정 코드와 지표는 지금 코드로 다시 계산한다.
새로 부를 호출이 있으면 방식별 건수와 예상 비용을 보여 주고 `y`를 받는다.

**비교 방식 구성**

| 비교 방식 | 입력 | 시스템 프롬프트 | 판정 주체 |
| --- | --- | --- | --- |
| LLM에 그냥 물음 (`llm_naive`) | 자연어 | 상태 **정의만** | LLM |
| LLM에 '모르면 모른다' 지시 (`llm_only`) | **같은 자연어** | 정의 + 보류 **지시** | LLM |
| LLM에 사실 데이터 줌 (`llm_with_facts`) | 구조화한 일정 + 사실 + 우리 기준 | 정의 + 지시 + **판정 규칙**(`RULES`) | LLM |
| 판정 코드 (`code`) | **같은 입력** | 같은 규칙을 코드로 | `verdict.py` |

```
그냥 물음 → '모르면 모른다' 지시     지시 효과        프롬프트로 보류를 유도하면 달라지는가
'모르면 모른다' 지시 → 사실 데이터    정보 제공 효과    사실 · 판정 규칙 · 입력 구조화가 섞여 있다
사실 데이터 → 판정 코드              판정 방식 효과    입력과 판정 규칙이 같으므로 그 차이만 남는다
```

판정 규칙(`RULES`)은 판정 코드가 쓰는 규칙을 그대로 적은 것이다 — 공휴일 시간표 우선, 정기휴일과 공휴일이 겹칠 때,
입장마감 정각, 회차 입장, 체류를 모를 때, 이동 0분 규칙과 권장 여유 미달, 택시 대안, 필수 일정. 3차 피드백에서 T15의
'공휴일 시간표 우선'을 판정 코드만 알고 있었다는 지적을 받고 넣었다. 사실 데이터가 없는 두 LLM 방식에는 규칙을 적용할 값이
없어 주지 않는다. 판정 코드의 규칙을 고치면 `RULES`도 고친다.

| 함수 | 하는 일 |
| --- | --- |
| `build_models` | LLM 출력 스키마. **코드 출력과 같은 모양**이어야 비교가 된다 |
| `facts_for_llm` | 'LLM에 사실 데이터 줌'과 판정 코드에 **완전히 같은** 사실 데이터를 준다 |
| `llm_requests` | 문제 하나에 LLM 방식마다 보낼 요청을 만든다. 이것으로 요청 지문을 만들고 그대로 부른다 |
| `answer` | 받아 둔 응답이 있으면 그것을 쓰고, 없으면 `core/llm.py`의 `ask`로 불러 받는 즉시 응답 캐시에 넣는다. 거부(refusal)는 `refused`, 형식 오류는 `invalid`로 남긴다 |
| `graded` | 한 방식의 답 하나를 정답과 대조한다 — 전체 판정, 기대 검사마다 상태(`labels.check_mismatches`), 검사 상태와 전체 판정이 맞물리나(`verdict.verdict_of`) |
| `metrics` | 아래 지표를 계산한다. 거부와 형식 오류는 답을 준 것으로 세지 않고 따로 센다 |
| `StubClient` | `--dry-run`용. API 없이 배선만 통과시킨다. 응답은 실제 호출과 같은 스키마 검증을 지난다 |

**공식 기록 `last-compare.json`은 모든 비교 방식 · 모든 문제를 한 조건에서 돌렸을 때만 쓴다.** `--arms`나 `--case`로 일부만 돌린 결과는 `last-compare-subset.json`에 따로 남는다. 예전에는 일부만 돌린 결과를 이전 기록에 얹었는데, 그러면 한 기록 안에 다른 정답 · 다른 코드로 낸 판정이 섞인다. 멘토 피드백 3번이 짚은 "옛 기대값이 남은 행"이 그렇게 생겼다. 게다가 진행 중 저장이 이전 기록을 먼저 덮어써서, LLM 비교 방식을 돌린 실행에서는 얹기 자체가 한 번도 제대로 된 적이 없었다.

**보는 지표**

| 지표 | 왜 보나 |
| --- | --- |
| 검사별 정확도 — 기대 검사 중 상태가 맞은 비율 | 전체 판정이 맞아도 검사가 틀릴 수 있다. T28은 전체가 보류라 맞았지만 삼청동 휴무 · 입장을 미확인 대신 해당 없음으로 답했다(3차 피드백). 사용자는 어느 검사가 틀렸는지를 보고 일정을 고친다 |
| 기대 검사를 답하지 않음 | 검사를 빠뜨린 것과 상태를 틀린 것을 나눠 본다 |
| 검사와 전체 판정이 어긋남 | 위반 검사가 있는데 전체가 가능인 답(T27)처럼 앞뒤가 안 맞는 답. 판정 코드는 같은 규칙(`verdict_of`)으로 전체 판정을 내므로 0이어야 한다 |
| 정밀도 — 불가능이라고 한 것 중 맞은 비율 | 헛경보를 얼마나 내나 |
| 재현율 — 정답이 불가능인 것 중 찾은 비율 | 얼마나 놓치나 |
| 가능인데 불가능 | 멀쩡한 일정을 막는가 |
| **불가능인데 가능** | 안 되는 일정을 괜찮다고 했나 |
| **보류인데 가능** | **가장 위험하다** — 확인하지 못한 일정을 괜찮다고 했나 |
| 보류 비율 | 얼마나 자주 답을 못 주나 |
| 답을 준 비율 | **전부 보류하면 지표는 완벽해지고 서비스는 쓸모없어진다** |
| 모델 거부 | 보류와 섞으면 모델이 판단을 보류한 건지 응답을 거부한 건지 구분되지 않는다 |
| 형식 오류 응답 | 스키마에 맞지 않는 응답도 판정이 아니다. 보류와 섞지 않는다 |

**중요한 결정** — 지시와 정의 분리 · 입력 일치 · 정확도만 보면 안 되는 이유 · 공식 기록은 전체 실행만 · 부르기 전에 응답 캐시와 맞춰 보고 묻는다

## `core/eval_report.py` — 평가 보고

| | |
| --- | --- |
| **역할** | 실행 기록 세 개(판정 · 구조화 추출 · 비교 실험)를 읽어 **총점 하나 대신 나눠서** 보여 준다 |
| **실행** | `python core/eval_report.py` — 키가 필요 없다. API를 부르지 않는다 |
| **출력** | 화면 + [`docs/eval-report.md`](eval-report.md) |

멘토 피드백 3번 — "최종 보고에는 총점 하나보다 오류 유형별 결과, 잘못된 정상 판정, unknown 비율과 원인, 비용/지연을
나눠 보여주세요." 보고서의 절이 이 순서다.

- **오류 유형** — 정답과 다르게 낸 답을 '정답인데 답' 짝으로 여섯 갈래로 나눈다. 위험한 순서로 보류인데 가능 · 불가능인데
  가능 · 가능인데 불가능 · 보류인데 불가능 · 불가능인데 보류 · 가능인데 보류다. 멘토가 말한 '잘못된 정상 판정'은 불가능인데
  가능이다. 정확도가 같아도 어느 갈래로 틀렸는지에 따라 위험이 다르다.
- **보류 원인** — 판정 코드가 보류한 문제마다 확인하지 못한 이유를 세고, 누가 풀 수 있는지(사용자 · 데이터 · 코드)로
  묶는다. 사용자에게 물어야 풀리는데 물을 말이 없는 검사도 찾아낸다.
- **검사별 채점** — 비교 방식마다 검사별 정확도, 답하지 않은 검사, 검사와 전체 판정이 어긋난 답. 전체 판정은 맞았는데 검사가
  틀린 문제를 따로 적는다(3차 피드백).
- **구조화 추출** — 항목별 점수와, 끝까지 돌렸을 때 틀린 건이 구조화 추출 탓인지 판정 탓인지.
- **세 기록의 조건이 다르면 경고한다.** 코드 커밋이나 입력 지문이 다른 숫자를 한 보고서에 섞지 않는다.

| 함수 | 하는 일 |
| --- | --- |
| `error_type` | 정답과 판정의 짝을 여섯 갈래 중 하나로 |
| `no_question` | 사용자가 풀어야 하는 보류인데 물을 말이 없는지 |
| `attribution` | 끝까지 돌린 한 건이 틀렸다면 어느 단계 탓인지 |
| `mismatched_conditions` | 세 기록의 코드 커밋과 입력 지문 비교 |

누가 푸는지는 `SOLVED_BY`에 이유마다 적었다. 판정 코드가 낼 수 있는 이유가 모두 들어 있는지 `tests/test_eval_report.py`가
`verdict.py`와 대조한다.

| | |
| --- | --- |
| **역할** | 실행 기록에 "어떤 조건에서 돌렸나"를 함께 남긴다 |

멘토 피드백 3번 — 같은 15/15라도 코드 · 정답 · 사실 데이터 · 우리 기준 · 프롬프트 · 기준 날짜가 다르면 다른 숫자다. 실행 기록마다 아래를 함께 적는다. 모델과 effort는 원래 기록에 있다.

| 항목 | 내용 |
| --- | --- |
| `code_commit` | 실행할 때의 git 커밋 |
| `uncommitted` | `core/`에서 커밋하지 않은 변경. 실행 기록(`last-*.json`)과 응답 캐시(`response-cache.json`)는 실행이 쓰는 출력이라 세지 않는다 |

| `fingerprints` | `tests.json` · `facts.json` · `policy.json`의 내용 지문(sha256 앞 12자리). 줄바꿈을 맞춰서 Windows와 다른 OS에서 같은 값이 나온다 |

| `prompts` | 구조화 추출 · 비교 실험 시스템 프롬프트와 출력 스키마의 지문 |
| `libraries` | `anthropic` · `pydantic` 버전. 출력 스키마를 만들고 검증하는 쪽이라, 같은 커밋이라도 버전이 다르면 모델이 받는 스키마가 달라질 수 있다 |

커밋하지 않은 변경이 있어도 실행은 막지 않는다. 개발 중에도 돌려 봐야 하기 때문이다. 대신 화면에 경고를 내고 기록에 `reproducible: false`로 적는다.

**중요한 결정** — 재현할 수 없는 실행도 막지 않고 그렇다고 적는다

## `core/model_info.py` — 기본 모델 · 단가 · 모델별 옵션

| | |
| --- | --- |
| **역할** | 구조화 추출과 비교 실험이 쓰는 기본 모델, 모델별 단가, 모델마다 받는 옵션, 호출 한 번의 비용 계산을 한 곳에 둔다 |
| **읽는 쪽** | `extract.py` · `run_extract.py` · `compare.py` |

기본 모델은 `claude-opus-5-5`다. 단가는 [공식 가격 페이지](https://platform.claude.com/docs/en/about-claude/pricing)에서 2026-10-01에 확인한 값을 그대로 적었다. 캐시 읽기 배수가 모델마다 달라서(Opus 5.5는 입력의 0.05배, 나머지는 0.1배) 입력 단가에 배수를 곱하지 않고 값으로 적는다. 단가를 모르는 모델은 비용을 `null`로 남긴다 — 다른 모델의 단가를 빌려 쓰면 틀린 비용이 기록되기 때문이다. Haiku 4.5는 effort를 받지 않아 보내지 않는다(보내면 400).

거부(refusal)된 호출은 [공식 문서](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback#how-refusals-are-billed)의 청구 규칙대로 센다(2026-10-01 확인). 출력이 나온 뒤의 거부는 입력과 나온 출력이 청구된다. 출력 전의 거부는 `bio` · `frontier_llm` · `reasoning_extraction` 분류일 때만 청구되고, 그 밖에는 usage에 토큰이 찍혀 있어도 0원이다. 토큰을 그대로 곱하면 비용이 부풀려진다.

**중요한 결정** — 캐시 단가를 배수가 아니라 값으로 적음

## `core/llm.py` — Claude 호출

| | |
| --- | --- |
| **역할** | 구조화 출력(JSON 스키마)으로 Claude를 한 번 부르고, 끝까지 온 응답만 스키마로 검증한다 |
| **입력** | `ask(client, model, effort, system, content, schema)`. 모델에 보내는 인자는 `request_params`가 만든다 |
| **출력** | `(검증된 결과, usage)`. 거부면 `Refusal`, 응답이 잘렸거나(`max_tokens`) 스키마에 맞지 않으면 `InvalidOutput`. 둘 다 사용량을 함께 넘긴다 |
| **읽는 쪽** | `extract.py` · `compare.py` · `run_extract.py` · `response_cache.py` |

SDK의 `messages.parse()`를 쓰지 않는다. `parse()`는 `stop_reason`을 보기 전에 본문을 스키마로 검증해서, 출력 도중 거부돼 JSON이 잘린 응답이면 거부를 확인하기도 전에 `ValidationError`로 실행이 멈춘다(anthropic 1.7.0 · 1.11.0에서 확인). 공식 문서도 거부된 응답의 부분 출력은 버리라고 한다. 그래서 `messages.create`로 받아 `stop_reason`을 먼저 보고, 끝까지 온 응답만 검증한다. 요청 스키마는 `parse()`와 같은 `transform_schema`로 만든다.

검증에 실패한 응답도 끝까지 온 응답이라 청구된다. 그래서 `InvalidOutput`에 사용량을 담아 넘기고, 평가 실행은 그 문제를 오류로 남긴 채 다음으로 넘어간다.

거부(refusal)가 나와도 다른 모델로 넘기는 설정(fallbacks)은 켜지 않는다. 평가하는 실행에서 다른 모델이 대신 답하면 그 결과는 이 모델의 결과가 아니다. 거부는 거부로 남긴다.

**중요한 결정** — `parse()` 대신 받은 뒤 검증 · 거부를 다른 모델로 넘기지 않음

## `core/response_cache.py` — 응답 캐시

| | |
| --- | --- |
| **역할** | 돈을 내고 받은 LLM 응답을 요청 지문별로 저장해 두고, 같은 요청이면 다시 부르지 않는다 |
| **읽는 쪽** | `run_extract.py` · `compare.py`. 실제 사용 경로(`verify.py` · `app.py`)는 쓰지 않는다 — 사용자가 넣은 일정은 저장하지 않는다 |
| **파일** | [`core/response-cache.json`](../core/response-cache.json) |

**왜 만들었나** — 2026-10-12 \~ 13에 화면 글만 바꾸고 전체 평가를 다시 돌려 같은 요청에 돈을 두 번 냈다. 잔액이 떨어져 도중에 멈춘 실행은 그때까지 받은 응답도 버렸다. 모델이 받는 것이 같으면 답을 다시 살 이유가 없다.

**같은 요청인지는 요청 지문으로 본다.** 모델 · 시스템 프롬프트 · 본문 · 출력 스키마 · effort · max_tokens, 곧 `llm.ask`가 실제로 보내는 인자 전부의 지문이다. 프롬프트나 사실 데이터가 한 글자라도 바뀌면 지문이 달라져 그 요청만 새로 부른다.
코드 커밋은 지문에 들어가지 않는다. 그래서 화면 글만 바꾼 커밋이나 커밋 메시지를 고친 뒤에도 기록을 지금 커밋으로 다시 만들 수 있다 — 채점과 판정은 지금 코드로 다시 하고, LLM 응답만 받아 둔 것을 쓴다.

| 함수 | 하는 일 |
| --- | --- |
| `request_key` | `llm.ask`가 받는 인자로 요청 지문을 만든다. 실제로 보내는 인자와 같은 함수(`llm.request_params`)를 쓴다 |
| `ResponseCache.put` | 응답을 받는 즉시 파일에 쓴다. 다음 호출에서 멈춰도 돈을 낸 응답은 남고, 다시 돌리면 남은 것만 부른다 |
| `confirm_spend` | API를 부르기 전에 새로 부를 호출 수와 예상 비용을 보여 주고 `y`를 받는다. 새로 부를 것이 없으면 묻지 않고 키도 받지 않는다 |
| `ResponseCache.estimate_usd` | 예상 비용을 넉넉히 어림한다 — 받아 둔 응답 중 가장 긴 입력 · 출력에, 방식마다 첫 호출 한 번의 프롬프트 캐시 쓰기를 더한다. 2026-10-14에 지난 평균으로 $0.40이라고 하고 $0.63이 나가서 바꿨다 |
| `cost_summary` | 응답 묶음의 비용과 지연. 받아 둔 응답도 받을 때의 사용량으로 센다 — 이번 실행에서 쓴 돈이 아니다(그건 `spend.py`) |

캐시에는 채점에 쓰는 모양으로 검증을 마친 답, 그 호출의 사용량, 받은 실행 번호를 둔다. 거부와 형식 오류도 답으로 둔다 — 평가에서는 그것도 결과다.
실행 기록의 `responses`에는 새로 받은 건수, 받아 둔 응답을 쓴 건수, 그 응답을 받은 실행, 이번 실행에서 나간 돈(`spent_usd`)이 남는다.

**받아 둔 응답을 다시 채점한 것과 새로 부른 것은 다른 숫자다(3차 피드백).** 받아 둔 응답을 다시 쓰는 실행은 LLM이 같은 입력에
답을 바꾸는지 보여 주지 않는다. 공식 기록은 문제마다 응답 하나로 내고, 흔들림은 `--repeat N`으로 따로 잰다 — 같은 요청을
N번 새로 부르고, 응답 캐시는 읽지도 쓰지도 않아 공식 기록에 쓴 응답을 바꾸지 않는다. 문제는 멘토 말대로 일부로 좁혔다.
구조화 추출은 오전 · 오후가 없는 시각(T12 · T22 · T23)과 꼭 타야 하는 열차가 있는 일정(T27 · T33), 비교 실험은
판정 규칙이 여럿 겹치는 문제(T15 · T17 · T27 · T28)를 'LLM에 사실 데이터 줌'으로 부른다. `--case`로 바꿀 수 있다.
2026-10-12 비교 실험 응답은 호출별 사용량을 남기기 전에 받아서 방식별 합계만 있다(`totals`). 그 묶음을 통째로 쓰면 합계에 새로 받은 응답의 비용을 더하고, 일부만 썼으면 비운다. 지연 중앙값은 묶음끼리 합칠 수 없어 비운다.

**중요한 결정** — 부르기 전에 캐시와 맞춰 보고 묻는다 (`run_extract.py` · `compare.py`)

## `core/routes.py` — TMAP 길찾기

| | |
| --- | --- |
| **역할** | 판정할 때 일정의 구간마다 TMAP 예상 이동시간을 받는다. 받은 값은 저장하지 않는다 |
| **입력** | `live_legs(itinerary, key, facts, policy)` |
| **출력** | `(legs, misses)` — 판정 코드의 `legs`에 덮어쓸 구간, 받지 못한 구간과 이유 |

날짜나 장소가 없거나 날짜와 요일이 어긋난 일정에는 TMAP을 부르지 않는다. 판정 코드가 입력부터 묻고 이동은 보지 않기
때문이다. 화면 서버(`app.py`)와 `verify.py`가 이 함수를 같이 쓴다.

장소 좌표는 TMAP 장소 검색으로 받는다. 이름이 같은 곳의 **입구 좌표**를 쓰고, 입구 좌표가 없으면 중심점을 쓴다.
"경복궁"을 찾았는데 첫 결과가 "경복궁역"일 수 있어서 첫 결과를 그대로 쓰지 않는다. TMAP 이름이 다른 곳은
`TMAP_NAMES`에 적는다 — 서울시립미술관 서소문본관은 "서울시립미술관"(덕수궁길 61), 서울역은 노선별로 나뉘어 있어
"서울역[KTX정차역]"이다(2026-10-05 확인). 이름이 비슷하면 받아 주는 식으로 느슨하게 맞추지 않는다 —
"서울시립미술관 주차장"도 비슷하다.

구간은 대중교통으로 묻는다. **HTTP 200이어도 "출발지와 도착지가 너무 가까움"(코드 11)이면 경로가 없다.**
그때는 걷기로 다시 묻는다. 받은 시간은 분 단위로 올림한다 — 내리면 늦는 일정을 통과시킬 수 있다.
받은 구간은 최소 이동시간이 아닌 예상치(`is_lower_bound: false`, `source: api_runtime`)라서, 늦어도 위반이 아니라
`LATE_BY_ESTIMATE`(미확인)가 된다.

출발 시각은 판정 코드의 입장 시각(`entry_at`)에 사용자가 말한 체류시간을 더한다. 개장 전에 도착하면 개장까지
기다린 뒤 이동하는 것으로 TMAP 대중교통 조회와 택시 예측의 출발 시각에 반영한다. 체류시간을 모르면 0분을 더한다.

**받은 구간은 구간 번호로 붙인다** — `0:서울시립미술관 서소문본관|경복궁`(출발 장소 순번), 필수 일정이면
`HC1:덕수궁|서울역`(`verdict.segment_key`). 같은 장소 사이를 오전 · 오후에 두 번 가면 출발 시각이 달라 값이 다르다 —
'출발|도착' 하나에 붙이면 오후 조회가 오전을 덮어써 오전 구간을 오후 값으로 통과시켰다(3차 피드백). 구간마다 받은
날짜 · 출발 시각(`depart_at`)을 함께 붙이고, 판정 코드는 이것이 판정할 때 계산한 출발 시각과 같을 때만 그 값을
쓴다(`verdict.leg_for`). 아니면 저장해 둔 값(출발|도착 — 최소 이동시간 · 테스트용 이동시간)을 쓴다.

**택시는 대중교통 구간의 대안으로 붙인다.** 타임머신 자동차 길 안내로 같은 출발 시각의 교통을 반영한 택시 시간과
요금을 받는다. `predictionType`은 이름과 반대로 `arrival`이 출발 시각 기준이다(2026-10-05 확인). 판정 코드는
대중교통으로 통과가 안 나올 때만 택시를 본다. 걸어갈 만큼 가까운 구간에는 붙이지 않고, 택시를 받지 못해도
대중교통 판정은 그대로 한다.

**429(너무 빨리 부름)는 기다렸다 다시 묻는다.** 2026-10-05에 대중교통을 연달아 네 번 부르자 네 번째가 429였다
(하루 무료 한도 안). TMAP이 기다릴 시간(`Retry-After`)을 주면 그만큼, 안 주면 1 · 2 · 4초 기다린다.

받지 못하면 이유를 나눠 남긴다 — `TIMEOUT` · `NETWORK_ERROR` · `RATE_LIMITED` · `HTTP_ERROR` ·
`UNPARSEABLE_RESPONSE` · `NO_ROUTE` · `PLACE_NOT_FOUND`. 그 구간은 저장해 둔 최소 이동시간이 있으면 그걸로, 없으면
'확인 못 함'으로 판정한다.

테스트는 가짜 응답으로 한다(`tests/test_routes.py`). 진짜 TMAP을 부르면 키와 요금이 들고, 인터넷이나 TMAP
사정으로 코드가 멀쩡해도 실패하며, 시간 초과 같은 상황은 일부러 만들 수 없다. 가짜 응답은 2026-10-02에
실제로 받은 모양과 공식 문서를 따랐고, TMAP이 정말 그렇게 답하는지는 `check-tmap-api.mjs`로 따로 확인한다.

**중요한 결정** — 429는 기다렸다 다시 물음 · 이름이 같은 장소만 씀 · HTTP 200이어도 경로가 없으면 걷기로 다시 물음 · 타임머신은 `predictionType` `arrival`(출발 시각을 넣는다)

## `core/verify.py` — 일정 하나 검증

| | |
| --- | --- |
| **역할** | 자연어 일정 하나를 구조화 추출하고(Claude), 구간마다 이동시간을 받고(TMAP), 판정해서 보여 준다 |
| **실행** | `python core/verify.py "일정"` — 키는 환경변수에 없으면 물어본다 |
| **남기는 것** | 없다. TMAP 값은 저장할 수 없어서 기록 파일을 쓰지 않는다 |

받은 구간은 판정 코드의 `legs`에 덮어써서 저장해 둔 지하철 최소 이동시간 대신 쓴다. 받지 못한 구간은 이유를 보여 주고,
저장해 둔 최소 이동시간이 있으면 그걸로, 없으면 '확인 못 함'으로 판정한다. 결과는 `run.py`와 같은 [결과] 묶음이고,
그 앞에 추출한 일정과 받은 이동시간(대중교통 · 도보, 택시 대안과 요금)을 보여 준다.

평가용 실행(`run.py` · `run_extract.py` · `compare.py`)과 달리 기록을 남기지 않는다. TMAP 값은 저장할 수 없고
날마다 달라질 수 있어서, 같은 일정을 다시 돌려도 같은 결과를 보장할 수 없다. 그래서 평가는 저장해 둔 데이터로 한다.

2026-10-05에 T01과 장소 세 곳짜리 일정(덕수궁 → 서울시립미술관 → 경복궁)을 실제 키로 돌려 둘 다 '가능'이
나왔다. 저장해 둔 최소 이동시간만 쓰면 둘 다 보류인 일정이다.

| `POST /api/recheck` | `original` — `/api/check`가 돌려준 처음 일정 / `revised` — 표에서 고친 일정 / `legs` — 처음 검사에서 받은 구간(생략 가능) | `legs` — 수정 일정용으로 새로 받은 구간 / `leg_misses` — 새 조회에서 받지 못한 구간과 이유 / `tmap` — 키 설정 여부 / `verdict_before` · `verdict_after` — 수정 전후 판정 / `changed_fields` — 바뀐 경로 / `needs_confirmation` — 필수 일정 · 날짜 · 가려던 장소를 바꾼 것의 확인 / `result` · `report` · `questions` · `timeline` — 수정 일정의 재검사 결과 |

요청 본문의 필드와 API 경로는 실행 중인 `/docs`와 `/openapi.json`에서 볼 수 있다. `/api/check`는 Anthropic 키가 없으면 `503`, 빈 입력이나 추출할 수 없는 일정은 `422`, Claude 호출 실패는 `502`를 돌려준다.
`/api/recheck`는 처음 일정과 고친 일정이 추출 결과와 같은 일정 모델(`extract.Itinerary`)에 맞지 않으면 판정 전에 `422`다 —
체류 -60 · 0 · 1441분이나 문자열 "60", 읽을 수 없는 날짜 · 시각. 체류를 비운 것은 잘못이 아니라 추가 질문과 보류다(3차 피드백). TMAP 키 없이도 앱은 열리고 저장해 둔 최소 이동시간으로 판정한다.

멘토는 얇은 API와 화면으로 이 흐름을 실제로 보여 달라고 했고, FastAPI 정도면 충분하다고 했다. 그래서 새 판정 로직은
없다. 구조화 추출 · 길찾기 · 판정 · 재검사 · 질문 모으기는 기존 파일(extract · routes · verdict · recheck · report)이 하고,
여기서는 잇기만 한다.

**표에서 고친 칸은 사용자가 말한 값으로 본다.** 추측한 날짜나 시각을 그대로 두면 추측으로 남고, 고치거나 "맞아요"에
체크하면 사용자가 말한 값이 된다. 말한 요일과 날짜가 어긋나면 날짜를 그대로 두고 그 날짜가 맞다고 할 수도 있다.
체류시간을 비워 두면 모르는 것으로 본다.

**원래 일정은 처음과 같은 이동시간으로 다시 판정한다.** 고친 일정은 고친 출발 시각으로 이동시간을 새로 받는다. 둘을
섞으면 같은 구간을 다른 시각의 값으로 판정해서 '수정 전' 판정이 처음 화면에서 본 것과 달라질 수 있다. 화면이 돌려준
값은 TMAP에서 오늘 받은 것만 다시 쓴다. TMAP 값은 받은 뒤 24시간 넘게 쓸 수 없기 때문이다([`docs/data-policy.md`](data-policy.md)).

**판정 코드가 먼저 묻는 일정이면 길찾기를 부르지 않는다.** 날짜나 시각이 빠졌거나 말한 요일과 날짜가 어긋나면 판정
코드는 이동을 보지 않고 그것부터 묻는다. 그때 길찾기를 부르면 쓰지 않을 값에 호출만 쓴다. 이 검사는 `routes.live_legs`
안에 있어서 `verify.py`도 똑같이 지킨다. 읽을 수 없는 시각은 그 전에 일정 모델이 `422`로 막는다.

**내 PC 주소로 온 요청만 받는다.** 다른 사이트가 자기 도메인을 127.0.0.1로 돌려 놓고 이 서버를 부르면(DNS 리바인딩이라는
공격이다) 브라우저는 같은 사이트로 보고 막지 않는다. 그러면 남의 페이지가 이 키로 Claude와 TMAP을 부를 수 있어서,
요청의 Host가 127.0.0.1이나 localhost가 아니면 거절한다.

`tests/test_app.py`가 FastAPI의 TestClient(서버를 띄우지 않고 API를 부르는 테스트 도구)로 두 API를 끝까지 부른다.
Claude와 TMAP은 여러 테스트가 같이 쓰는 `tests/helpers.py`의 가짜를 쓴다.

## `check-places-api.mjs` — Places API 능력 확인

| | |
| --- | --- |
| **역할** | Places API가 **판정에 필요한 필드를 주는지** 확인한다 |
| **실행** | `GKEY=... node check-places-api.mjs` |
| **대상** | 지원 후보 12곳 |

`TARGETS`에 장소와 기대 휴무 요일, 공식 출처를 적어두고 응답과 대조한다. `FIELD_MASK`로 요청 필드를 지정한다.

**결과** — 12곳 전부 `regularOpeningHours`를 반환했다. 그런데 판정에 필요한 것으로 보면

| 필요한 것 | 제공 |
| --- | --- |
| 요일별 운영시간 · 정기휴일 | ✅ |
| 입장마감 · 계절별 시간표 · 공휴일 예외 규칙 · 적용기간 | ❌ **전부 없음** |

**채움률만 재면 12/12로 보인다.** 그래서 이 프로젝트는 운영정보를 공식 페이지에서 옮겨 적고(`curated`) Google은 `place_id`에만 쓴다.

> 응답 원문은 이 레포에 저장하지 않는다. 약관상 저장이 허용되는 것은 `place_id`와 lat/lng(30일)뿐이다.

## `check-routes-api.mjs` — Routes API 모드 확인

| | |
| --- | --- |
| **역할** | 이동수단별로 경로가 오는지 확인한다 |
| **실행** | `GKEY=... node check-routes-api.mjs` |

| 모드 | 결과 |
| --- | --- |
| `TRANSIT` | 경로 반환 |
| `WALK` | **경로 없음** (HTTP 200, 빈 결과) |
| `DRIVE` | **경로 없음** (HTTP 200, 빈 결과) |

**HTTP 200인데 결과가 비어 있다.** 이 상태를 "조회했다"로 처리하면 실패가 정상으로 바뀐다. 데이터를 가져오는 쪽에서 `시간 초과 / 응답 없음 / 필수 필드 누락`을 구분해야 하는 이유가 이것이다.

조회 스크립트는 실패를 `TIMEOUT`, `NETWORK_ERROR`, `HTTP_ERROR`,
`UNPARSEABLE_RESPONSE`로, 결과가 없으면 경로 스크립트는 `NO_ROUTE`, 장소·이동시간 조회 스크립트는 `NO_RESULT`로 기록한다. 이 값은 API에서 관찰한
상태이며, 판정 코드의 통과 · 위반 · 미확인 해석과 섞지 않는다.

도보 구간을 Routes API로 해결할 수 없다는 것이 여기서 확인됐다.

## `fetch-travel-times.mjs` — Routes API 이동시간 조회

| | |
| --- | --- |
| **역할** | 7구간 대중교통 이동시간 조회 + 도보 근사와 비교 |
| **실행** | `node fetch-travel-times.mjs` — 키를 터미널에서 입력받는다 |

출발 시각을 **고정한다.** 그래야 다시 받아도 같은 조건의 값이 나온다. `straightMeters`로 하버사인 직선거리를 구해 우회계수 1.3, 보행속도 4km/h로 도보를 근사한다.

**관찰** — 짧은 구간에서 대중교통 경로가 도보 근사보다 오래 걸렸다. 응답을 보면 도보 → 탑승 → 도보로 쪼개져 있고 대기시간이 붙는다. 확인된 문제는 "예측이 틀렸다"가 아니라 **"구간에 맞는 이동수단을 고르지 않았다"** 다.

> **현재 판정에는 쓰지 않는다.** 응답 값(소요시간·거리)은 약관상 저장할 수 없다.
> 이동시간은 공공누리 지하철 데이터로 교체했다.

## `check-tmap-api.mjs` — TMAP 모드 확인

| | |
| --- | --- |
| **역할** | TMAP이 장소 검색으로 좌표를 주는지, 서울 구간에서 수단별로 경로를 주는지, 자동차는 출발 시각을 넣어 예측하는지 확인한다 |
| **실행** | `node check-tmap-api.mjs` — 키를 터미널에서 입력받는다 |

받은 좌표 · 시간 · 요금은 약관상 저장할 수 없어서 여기 적지 않는다. 경로 결과는 2026-10-05에
장소 검색의 입구 좌표로 물은 것이고, 괄호 안은 10-02(예전 `facts.json` 좌표)와 달랐던 점이다.

| 수단 | 구간 | 결과 |
| --- | --- | --- |
| 장소 검색 | 6곳 | 모두 찾았다. 서울시립미술관 서소문본관은 "서울시립미술관"(덕수궁길 61), 서울역은 "서울역[KTX정차역]"(한강대로 405)으로 맞춰야 했다 |
| 대중교통 | 서울시립미술관 → 경복궁 (10-08 14:00 출발) | 경로 반환 |
| 대중교통 | 광장시장 → 서울역 (10-08 19:30 출발) | 경로 반환 |
| 대중교통 | 경복궁 → 광장시장 (2027-03-05 15:00 출발) | 경로 반환 — 5개월 뒤 출발도 된다 |
| 대중교통 | 덕수궁 → 서울시립미술관 | 경로 반환 (10-02에는 **결과 없음** — HTTP 200, 코드 11 "출발지와 도착지가 너무 가까움") |
| 걷기 | 덕수궁 → 서울시립미술관 | 경로 반환 |
| 걷기 | 경복궁 → 창덕궁 | 경로 반환 |
| 자동차 | 광장시장 → 서울역 | 경로 반환, 택시 요금 포함 |
| 자동차 예측 | 광장시장 → 서울역 (10-08 19:30 출발) | 출발 19:30 그대로, 도착 예측과 택시 요금 반환 |
| 자동차 예측 | 경복궁 → 광장시장 (2027-03-05 15:00 출발) | 반환 — 5개월 뒤 출발도 된다 |
| 자전거 | — | 공개 API 목록에 없어 부르지 않았다 |

Google과 달리 대중교통 · 걷기 · 자동차가 모두 왔다. 다만 아주 가까운 구간은 대중교통이 HTTP 200에 결과 없이
올 수 있다(10-02). 이걸 "조회했다"로 처리하면 안 되고, 걷기 경로로 다시 물어야 한다. 같은 구간도 출발점 좌표에
따라 결과가 크게 달라져서, 좌표는 모두 TMAP 입구 좌표 하나로 맞춘다. 10-05 첫 실행에서는 대중교통 네 번째
호출이 429 THROTTLED였다(하루 무료 한도 안). 다시 돌렸을 때는 나오지 않았다.

자동차 예측은 처음에 `predictionType`을 `departure`로 보냈다. 그러자 넣은 19:30이 **도착** 시각으로 쓰였다 —
`departure`는 "출발 시각을 예측"한다는 뜻이었다. 출발 시각을 넣고 도착을 받으려면 `arrival`을 써야 한다.
시각을 넣지 않은 자동차 경로와 저녁 출발 기준 예측은 같은 구간인데도 시간이 달랐다. 택시는 계획한 시각으로 묻는다.

**스크립트가 덮어쓰는 파일이다.** 의미 있는 실행 결과는 그때그때 커밋해두는 것이 안전하다 — 실제로 한 번 잃었고 git 커밋에서 복원했다.
커밋해서 남길 기록은 실행 조건이 `reproducible: true`인 것이어야 한다. 코드를 먼저 커밋하고 돌린 기록이라는 뜻이다.
응답 캐시는 돈을 내고 받은 응답이라 기록과 함께 커밋한다. 커밋해 두면 누구든 같은 기록을 키 없이 다시 만들 수 있다.
기록을 다시 만들면 `python core/eval_report.py`로 평가 보고(`docs/eval-report.md`)도 다시 만든다.
