# 용어

이 프로젝트에서 쓰는 말을 정리한다. **★ 표시는 이 프로젝트가 정한 말**이고, 나머지는 일반 용어다.

읽는 순서 — 판정 결과 → 데이터 → 테스트 → 비교 실험

---

## 0. 바쁘면 이것만

**★ 이 다섯 개를 알면 나머지는 읽다가 찾아보면 된다.**

| 말 | 한 줄 설명 |
| --- | --- |
| **`unknown`** | "확인 못 했다". `pass` 도 `fail` 도 아닌 **제3의 답** |
| **누출** | "확인 못 했다" 를 "문제 없다" 로 답한 것. **가장 나쁜 실패** |
| **하한선** | 실제보다 작다고 보장된 값. **한 방향으로만** 판정할 수 있다 |
| **라벨** | 사람이 손으로 만들어둔 **정답** |
| **arm** | 비교할 **방식 하나** (LLM만 / 데이터 준 LLM / 코드) |

### 기본 용어 — 여행 일정 쪽 말

| 말 | 뜻 |
| --- | --- |
| **스톱** | 일정에 들어간 방문 장소 하나. `"1시 경복궁, 3시 광장시장"` 이면 스톱 2개 |
| **체류시간** | 그 장소에 머무는 시간. `"두 시간 볼 거예요"` 의 두 시간 |
| **입장마감** | **폐장 시각과 다른 값.** 경복궁 10월은 입장마감 17:00, 폐장 18:00 — 17:00 이후엔 들어갈 수 없다 |
| **정기휴일** | 매주 쉬는 날. 경복궁은 화요일, 창덕궁·덕수궁은 월요일 |
| **대체공휴일** | 공휴일이 주말과 겹치면 평일 하루를 대신 쉬는 제도. 2026-10-05가 그렇다 |
| **버퍼** | **우리가 얹는 안전 여유.** 사실이 아니라 우리 설정이다. 구간 이동 10분, 열차 탑승 15분 |
| **구간 (leg)** | 스톱에서 다음 스톱으로 가는 이동 한 번 |

### 기본 용어 — 이 프로그램의 두 단계

```
[추출]  자연어  →  구조
        "10월 8일 목요일 오후 1시에 경복궁 두 시간"
          ↓
        { date: "2026-10-08", stops: [{place:"경복궁", start:"13:00", dwell_minutes:120}] }
        담당: LLM

[판정]  구조 + 사실 + 정책  →  검사 결과
        담당: 코드 (verdict.py)
```

| 말 | 뜻 |
| --- | --- |
| **추출** | 자연어를 구조로 **옮겨 적는** 단계. 값을 채우지 않는다 |
| **판정** | 그 구조로 실행 가능성을 **검사하는** 단계 |
| **판정 코어** | 판정을 하는 코드(`verdict.py`). 외부 API를 부르지 않아서 "코어" |
| **조회 계층** | 외부에서 데이터를 가져오는 부분. 판정 코어와 분리해뒀다 |

## 1. 판정 결과를 읽을 때

### 검사 4상태 — `pass` / `fail` / `unknown` / `not_applicable`

검사 **하나**에 대한 결과다. 참/거짓 두 개가 아니라 네 개인 것이 이 프로젝트의 출발점이다.

| 상태 | 뜻 | 예시 |
| --- | --- | --- |
| `pass` | 근거를 **확보했고** 조건을 만족했다 | 경복궁 10월 입장마감 17:00 · 14:00 도착 |
| `fail` | 확보한 근거에서 위반이 **확인됐다** | 같은 근거 · 17:30 도착 |
| `unknown` | 검사가 **필요한데 끝내지 못했다** | 광장시장 영업시간을 확보하지 못했다 |
| `not_applicable` | 검사 **자체가 성립하지 않는다** | 휴무일로 확정된 곳의 운영시간 검사 |

**`unknown` 과 `not_applicable` 은 전혀 다르다.** 여기서 헷갈리면 서비스가 거짓말을 한다.

```
광장시장 영업시간을 모른다   →  검사는 **필요하다**. 끝내지 못했을 뿐  →  unknown
휴무일로 확정된 곳의 운영시간 →  검사가 **불필요하다**               →  not_applicable
```

> 검사가 **불필요**하면 `not_applicable`, 검사가 **필요한데 못 끝냈으면** `unknown`.

### 전체 판정 — `feasible` / `infeasible` / `undetermined`

일정 **전체**에 대한 결과다. 검사 여러 개를 합쳐 **가장 나쁜 상태**로 정한다. 다수결이 아니다.

| 판정 | 조건 | 사용자에게 보여주는 문장 |
| --- | --- | --- |
| `infeasible` | `fail` 이 **하나라도** 있다 | "확인한 정보에서 실행할 수 없는 부분이 발견되었습니다" |
| `undetermined` | `fail` 은 없지만 `unknown` 이 있다 | "위반은 발견되지 않았지만 N개 항목을 확인하지 못했습니다" |
| `feasible` | 필요한 검사가 **모두** 통과했다 | "확인한 정보와 검사 범위 내에서 위반이 발견되지 않았습니다" |

**`feasible` 일 때도 "실행 가능한 일정입니다" 라고 말하지 않는다.** 예약·날씨·혼잡도는 검사 범위 밖이라 보장할 수 없는 말이다.

### ★ 누출 (漏出)

`미확인을 통과로 낸 건수` · 코드에서는 `leaked_undetermined_as_feasible`

> **정답이 `undetermined`(확인 못 했다)인데 `feasible`(문제 없다)로 답한 경우**

**이 프로젝트가 막으려는 단 하나의 실패다.**

```
T14  "2027년 3월 5일 금요일 오후 1시에 경복궁 두 시간 보려고요."

     우리가 가진 근거 — 경복궁 운영시간. 단 2026년 기준이고 2026-12-31 까지 유효
     방문일이 2027년 → 이 근거를 쓸 수 없다 → 2027년에 몇 시에 여는지 모른다

     정답            undetermined  "확인 못 했습니다"
     llm_naive 답    feasible      "문제 없습니다"      ← 누출
```

**틀린 답보다 나쁘다.**

```
"확인 못 했습니다"  →  사용자가 직접 경복궁 홈페이지를 본다
"문제 없습니다"     →  사용자가 그냥 간다
```

그래서 `run.py` 요약에 이렇게 박아뒀다 — `(0이 아니면 다른 지표를 볼 필요가 없다)`.
정확도가 99%여도 누출이 1건 있으면 검증 서비스로는 실패다.

### `severity` — `blocking` / `warning`

`status` 와 **다른 질문**이다.

| | 묻는 것 |
| --- | --- |
| `status` | 지금 정보로 **확정할 수 있나** |
| `severity` | 실패하면 **타격이 큰가** |

KTX를 놓치는 건 정보가 부족해도 여전히 치명적이다. 그래서 `unknown` 이라고 `severity` 를 낮추지 않는다. 낮추면 "중요도 낮음" 으로 보여서 사용자가 확인을 건너뛴다.

### ★ `unknown_reason` — 왜 못 끝냈나

같은 `unknown` 이라도 **해결 방법이 다르므로** 따로 적는다.

| 이유 | 뜻 | 어떻게 해결하나 |
| --- | --- | --- |
| `NO_CLOSED_DAY_DATA` | 휴무일 정보를 못 구했다 | 데이터 확보 |
| `NO_OPERATING_HOURS_DATA` | 운영시간을 못 구했다 | 데이터 확보 |
| `EVIDENCE_EXPIRED` | 근거의 적용 기간이 지났다 | 재조회 |
| `PLACE_NOT_RESOLVED` | 장소를 특정하지 못했다 | 사용자에게 물어본다 |
| `HOLIDAY_CALENDAR_UNVERIFIED` | 공휴일 캘린더가 미검증이다 | API 호출 |
| `UNVERIFIED_TRAVEL_TIME` | 그 구간 이동시간이 없다 | 데이터 확보 |
| `ESTIMATE_ONLY` | 직선거리 근사값뿐이다 | 실제 경로 확인 |
| `LOWER_BOUND_ONLY` | 주행시간 하한선뿐이다 | 도보·환승·대기 확보 |
| `DEPENDS_ON_DEFAULT_DWELL` | 우리가 정한 기본값이 판정을 갈랐다 | 사용자에게 물어본다 |
| `UNSUPPORTED_ADMISSION_TYPE` | 정보는 있는데 **검사가 없다** | 코드를 고친다 |
| `UNVERIFIED_ALWAYS_OPEN` | 상시 개방 근거를 안 잡았다 | 공식 출처 확인 |

마지막 두 개가 중요하다. **"정보가 없다" 와 "검사가 없다" 는 다르다.** 앞은 데이터를 모으면 되고 뒤는 코드를 고쳐야 한다.

## 2. 데이터를 볼 때

### ★ 사실(facts) 과 정책(policy)

**두 파일로 나눠놓은 이유가 있다.**

| | `facts.json` | `policy.json` |
| --- | --- | --- |
| 뭐가 들어가나 | 운영시간·휴무일·이동시간·공휴일 | 기본 체류시간·버퍼·판정 기준 |
| 출처 | 공식 페이지 · 공공데이터 | **우리가 정한 값. 출처 URL이 없다** |
| 바뀌면 | 세상이 바뀐 것 | 우리 생각이 바뀐 것 |

한 파일에 두면 판정 결과를 보고 **"이게 공식 정보인가 우리가 정한 값인가"** 를 구분할 수 없다.

`policy.json` 첫 줄에 이렇게 적어뒀다 — *"전부 우리가 정한 값이다. 출처 URL이 없다. 사실이 아니라 설정이다."*

현재 정책값:

| | 값 | 뜻 |
| --- | --- | --- |
| `default_dwell_minutes` | 궁궐 90 · 미술관 60 · 시장식사 60 · 거리 45 | 체류시간을 안 말했을 때 쓰는 기본값 |
| `buffer_minutes.transit_leg` | 10분 | 구간 이동에 두는 여유 |
| `buffer_minutes.rail_boarding` | 15분 | 열차 탑승 전 권장 도착 여유 |
| `dwell_uncertainty_ratio` | 0.5 | 기본값을 ±50% 흔들어본다 |
| `require_user_dwell_for_completion_check` | true | 체류시간을 안 말했으면 체류 검사를 안 한다 |

### 근거 (evidence)

값 하나에 붙는 출처 정보다. **값만 있으면 근거가 아니다.**

| 필드 | 뜻 | 없으면 |
| --- | --- | --- |
| `source` | 어디서 왔나 (아래 표) | 스냅샷에 넣어도 되는지 판단 못 함 |
| `url` | 원 페이지 주소 | 다시 확인할 수 없음 |
| `checked_at` | 언제 확인했나 | 얼마나 오래된 값인지 모름 |
| **`valid_until`** | **언제까지 쓸 수 있나** | 작년 시간표로 올해를 판정함 |
| `rule_text` | 공식 안내 문구 원문 | 페이지가 바뀌었을 때 비교 기준이 없음 |
| `verified_by` | 확인 방법 | 정말 확인했는지 알 수 없음 |

**`source` 값이 뜻하는 것** — 이 값으로 *"레포에 저장해도 되는가"* 를 판단한다.

| 값 | 뜻 | 저장 |
| --- | --- | --- |
| `curated` | **사람이 공식 페이지를 읽고 옮긴 것.** 국가유산청·서울시립미술관 | ✅ |
| `public_data` | 공공데이터. 공공누리 1유형 또는 이용허락범위 제한 없음 | ✅ |
| `field_measured` | 사람이 실제로 이동해서 측정한 값 | ✅ |
| `api` | 상업 API 응답 (Google·TMAP) | ❌ 약관상 불가 |

`curated` 가 "사람이 손으로 넣었다" 는 뜻이라 얼렁뚱땅 들리지만, **오히려 가장 믿을 수 있는 출처**다.
공식 페이지 문구를 그대로 옮기고 URL·확인일·확인 방법을 함께 남기기 때문이다.
상업 API는 값이 자동으로 오는 대신 입장마감·계절별 시간표 같은 필드가 아예 없다.

### ★ 적용 기간 (`valid_until`)

> 오늘 조회했다는 사실만으로 다음 달 방문일에 쓸 수 있는 정보가 되지는 않는다.

T14가 이걸 검사한다. 경복궁 운영시간은 2026년 안내 기준이고 `valid_until: 2026-12-31` 이다. 2027년 방문일에는 **근거가 있어도 쓸 수 없다.**

Google Places 응답에는 이 개념이 **아예 없다.**

### ★ 스냅샷 / `snapshot_id`

`facts.json` 전체의 **버전**이다. 현재 `facts-2026-09-22`.

데이터가 바뀌면 이 값을 올린다. 그래야 *"이 판정 결과는 어느 데이터로 나온 것인가"* 를 되짚을 수 있다.

`snapshot_history` 에 버전별로 무엇이 바뀌었는지 남긴다. 그게 **라벨 노후화 검출**의 근거가 된다 (아래 참조).

### ★ 하한선 (lower bound)

**실제 값보다 작다는 것이 보장된 값.**

지금 이동시간은 지하철 **주행시간**뿐이다. 빠진 것 —

```
장소 → 역 도보        없음
환승 이동시간          없음
열차 대기시간(배차)    없음
```

| 구간 | 주행시간 하한선 |
| --- | --- |
| 미술관 → 경복궁 | 6.5분 (환승 1회) |
| 경복궁 → 광장시장 | 4.5분 (환승 1회) |
| 광장시장 → 서울역 | 7.0분 (환승 0회) |

빠진 몫이 얼마인지는 **모른다.** 그래도 판정은 할 수 있다.
크기를 몰라도 부호를 알기 때문이다 — 빠진 값은 언제나 0보다 크다.

**하한선은 한 방향으로만 쓸 수 있다.**

```
하한선으로도 늦는다   →  fail 확정    빠진 값을 더하면 더 늦어질 뿐이다
하한선으로는 도착한다 →  unknown      나머지를 모르니 확정할 수 없다
```

이걸 **하한선의 비대칭**이라고 부른다.

### ★ 민감도 검사 (±50%)

기본값으로 채운 체류시간을 **흔들어 보고, 판정이 뒤집히면 확정하지 않는다.**

```
T12  "10월 8일 목요일 오후 1시에 경복궁 보고 3시 15분에 광장시장 갈게요."

     체류시간을 안 말했다 → 궁궐 기본값 90분 적용
       45분 (90 × 0.5)  →  13:59 도착  →  15:15 전, 괜찮다
      135분 (90 × 1.5)  →  15:29 도착  →  15:15 후, 늦는다

     우리가 정한 값 때문에 판정이 갈린다  →  unknown
```

기본값을 쓰는 것 자체는 문제가 아니다. **그 기본값으로 계산한 결과를 사용자 일정의 확정적인 오류처럼 보여주는 것**이 문제다.

### 회차 입장 (`timed_entry`) / 상시 개방 (`always_open`)

| | 뜻 | 지금 상태 |
| --- | --- | --- |
| `timed_entry` | 정해진 시각에만 입장 (종묘 월·수·목·금, 해설사 동반 50분) | 검사 미구현 → `UNSUPPORTED_ADMISSION_TYPE` |
| `always_open` | 운영시간 개념이 없음 (청계천·덕수궁 돌담길) | 근거 미확보 → `UNVERIFIED_ALWAYS_OPEN` |

`always_open` 을 `not_applicable`(검사 불필요)로 두고 싶지만, **상시 개방임을 확인하지 않았으면 그것도 추측이다.** 확인 전에는 `unknown` 이다.

## 3. 테스트를 볼 때

### 골든 테스트 / 라벨

| | 뜻 |
| --- | --- |
| **골든 테스트** | 사람이 손으로 정답을 만들어둔 케이스 모음. 현재 15개 |
| **라벨** | 그 정답. `tests.json` 의 `expect` 와 `why` |

**라벨을 만들 때 판정 코드를 보지 않는다.** 코드로 정답을 만들고 그 코드가 맞혔다고 평가하면 규칙의 오류를 영원히 발견할 수 없다.

케이스 하나에 들어가는 것:

| 필드 | 내용 |
| --- | --- |
| `raw` | 입력 자연어 원문 |
| `date` · `stops` · `hard_constraints` | **기대 추출값** — LLM이 이렇게 뽑아야 한다 |
| `expect_applied` | 적용해야 하는 사실·가정·빠진 정보 |
| `expect` · `expect_checks` | **기대 판정** |
| `why` | 왜 그 판정인지 (라벨의 근거) |

### `dev` / `holdout`

| | 뜻 |
| --- | --- |
| `dev` | 개발 중 확인용. 9건 |
| `holdout` | 최종 성능 확인용. **구현을 여기 맞추지 않는다.** 6건 |

`holdout` 은 "시험 문제를 미리 안 보는" 것과 같다. 다만 **현재 15건은 전부 결과를 본 상태**라, 진짜 최종 확인용 케이스는 새로 만들어야 한다.

### ★ 라벨 노후화

> **같은 입력인데 데이터가 바뀌어서 정답이 달라진 상태**

라벨은 판정 코드와 독립이어야 하지만 **데이터 스냅샷과는 독립일 수 없다.**

```
T10  "10월 8일 목요일 오후 2시에 창덕궁 한 시간 반 보려고요."   ← 입력은 안 바뀜

     전   정답 undetermined   "창덕궁 관람시간을 확보하지 못했다"
          ↓  창덕궁 관람시간을 공식 페이지에서 확보함
     후   정답 feasible        09:00~18:00, 입장마감 17:00 → 14:00 도착 OK
```

**이걸 방치하면 핵심 지표가 거짓 경보를 낸다.** 실제로 `미확인을 통과로 낸 건수: 1` 이 떴는데, 코드 버그가 아니라 라벨이 낡은 것이었다.

그래서 `run.py` 가 자동으로 검출한다. **케이스가 의존하는 데이터가 바뀌었을 때만** 미검토로 본다.

| 표시 | 뜻 |
| --- | --- |
| `✅` | 검토된 라벨과 일치 |
| `❌` | 검토된 라벨과 불일치 — **실제 문제** |
| `⚠ 미검토(일치)` | 검토되지 않은 라벨과 맞았을 뿐 |
| `⚠ 미검토(불일치)` | 데이터가 바뀌어 정답이 달라졌을 가능성 |

> 판단할 때 **판정 코드의 출력을 보지 않는다.** "코드 출력이 라벨과 다르면 라벨이 낡은 것" 으로
> 하면 코드에 진짜 버그가 있을 때도 넘어가 버린다. 케이스의 장소 목록과 바뀐 키 목록,
> **데이터끼리만** 비교한다.

## 4. 비교 실험을 볼 때

### arm

**비교할 "방식" 하나하나.** 의학 임상시험에서 쓰는 말(대조군/실험군)을 그대로 썼다.

`code` 만 돌려서 15/15가 나왔다고 해도, 그게 데이터를 잘 모아서인지 규칙을 잘 짜서인지 아니면 LLM에게 그냥 물어봐도 됐을 일인지 알 수 없다. 그래서 **한 번에 하나씩만 바꿔가며** 비교한다.

| arm | 무엇을 주나 | 판정하는 쪽 |
| --- | --- | --- |
| `llm_naive` | 자연어 일정만 | LLM · **아무 지시 없음** |
| `llm_only` | **같은** 자연어 일정만 | LLM · "근거 없으면 모른다고 해라" **지시 추가** |
| `llm_with_facts` | 자연어 + 사실 데이터 + 정책 | LLM |
| `code` | **같은 것** | `verdict.py` |

```
llm_naive  →  llm_only          지시만 추가       →  지시의 효과
llm_only   →  llm_with_facts    데이터만 추가     →  데이터의 효과
llm_with_facts → code           판정 주체만 교체  →  코드의 효과
```

### 지표

| 지표 | 뜻 | 왜 보나 |
| --- | --- | --- |
| **전체 정확도** | 15건 중 몇 건 맞췄나 | 기본 |
| **정밀도** | `infeasible` 이라고 **한 것 중** 실제로 그런 비율 | 헛경보를 얼마나 내나 |
| **재현율** | 실제 `infeasible` **중** 잡아낸 비율 | 얼마나 놓치나 |
| **오탐** | 정상 일정을 `infeasible` 로 낸 건수 | 멀쩡한 일정을 막나 |
| **잘못된 일정 정상 통과** | 실제 `infeasible` 을 `feasible` 로 낸 건수 | 치명적 |
| **★ 누출** | 실제 `undetermined` 를 `feasible` 로 낸 건수 | **가장 치명적** |
| **★ 판정 보류 비율** | `undetermined` 를 낸 비율 | 얼마나 자주 답을 못 주나 |
| **★ 유효 판단 제공 비율** | 보류가 **아닌** 답을 준 비율 | 쓸모가 있나 |

**정밀도와 재현율은 헷갈리기 쉽다.** 분모가 다르다.

```
실제로 오류인 일정이 6건 있다. 검증기가 5건을 "오류" 라고 표시했고 그 5건이 다 맞았다면

  정밀도 = 5 / 5 = 1.0     분모는 "내가 오류라고 한 것"   → 헛소리를 안 했다
  재현율 = 5 / 6 = 0.833   분모는 "실제 오류 전체"        → 1건을 놓쳤다
```

`llm_naive` 가 정확히 이 숫자다 — 오류라고 한 건 전부 맞았지만(정밀도 1.0) 1건을 놓쳤다(재현율 0.833).

**마지막 두 개를 같이 봐야 하는 이유** —

모든 일정을 `undetermined` 로 내는 검증기는 누출 0, 오탐 0으로 **지표가 완벽해 보인다.** 그런데 사용자는 아무 답도 받지 못한다. 실제로 `llm_only` 가 그랬다.

| arm | 누출 | 유효 판단 | |
| --- | --- | --- | --- |
| `llm_naive` | 6 | 0.867 | 많이 답하지만 근거가 없다 |
| `llm_only` | **0** | **0.0** | 안전하지만 쓸모없다 |
| `llm_with_facts` | 1 | 0.6 | |
| `code` | **0** | **0.533** | **틀린 확신 없이 답을 준다** |

### 표본이 작을 때 조심할 것

현재 15건이다. 정답 분포는 `infeasible` 6 · `feasible` 2 · `undetermined` 7.

| | 읽을 수 있나 |
| --- | --- |
| 정밀도 · 재현율 | ⚠️ 분모가 6이라 1건 차이가 17%p를 움직인다 |
| 오탐 | ❌ 분모가 `feasible` 2건이라 **사실상 정보가 없다** |
| **누출 건수** | ✅ **"있다" 를 확정하는 쪽이라 표본이 작아도 유효하다** |
| 보류 비율 · 유효 판단 비율 | ✅ 비율로 읽을 수 있다 |

> 실제로 이걸 틀린 적이 있다. 7건만 채점했던 중간 결과에서 `llm_naive` 와 `code` 의 보류율이
> 둘 다 0.286으로 나왔다. 그래서 **"판단한 양이 같은데 코드가 더 정확하다"** 고 읽었다.
> 그런데 15건으로 채점하니 **0.133 대 0.467** 로 전혀 달랐다 — `llm_naive` 가 훨씬 많이 답한다.
> 표본이 작을 때 비율을 해석하면 이런 일이 생긴다.
