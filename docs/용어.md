# 용어

이 프로젝트에서 쓰는 말을 정리한다. 처음 읽는 사람이 설명 없이 알아들을 수 있는 말을 고르고(2026-10-11 정리),
비슷한 도구가 이미 쓰는 말이 있으면 그 말을 따랐다. 코드와 데이터 파일 안의 값은 영어 그대로 두고, 아래 대응표로 잇는다.

읽는 순서 — 판정 결과 → 데이터 → 정답 문제 → 비교 실험

## 0. 바쁘면 이것만

이 다섯 개를 알면 나머지는 읽다가 찾아보면 된다.

| 말 | 한 줄 설명 |
| --- | --- |
| **보류** | 확인하지 못한 것이 있어서 가능하다고도 불가능하다고도 하지 않은 판정. 세 번째 답이다 |
| **보류인데 가능** | 정답은 보류인데 "가능"이라고 답한 것. 확인하지 못한 일정을 괜찮다고 한 셈이라 **가장 나쁜 오류**다 |
| **최소 이동시간** | 지하철 탑승 시간만 센 값. 걷기 · 환승 · 대기가 빠져서 실제로는 이보다 더 걸린다 |
| **정답** | 사람이 공식 근거를 보고 미리 적어 둔 판정 |
| **비교 방식** | 비교 실험에서 견주는 판정 방법 하나 (LLM에 그냥 물음 · 사실 데이터를 준 LLM · 판정 코드 등) |

### 읽는 말과 코드 값

글과 화면에서는 왼쪽 말을 쓰고, 코드와 데이터 파일(`tests.json` · 실행 기록 · 판정 결과)에는 오른쪽 값이 남는다.

| 읽는 말 | 코드 · 데이터 값 |
| --- | --- |
| 가능 · 불가능 · 보류 | `feasible` · `infeasible` · `undetermined` |
| 통과 · 위반 · 미확인 · 해당 없음 | `pass` · `fail` · `unknown` · `not_applicable` |
| 치명 · 주의 | `severity: blocking` · `warning` |
| 정답 · 정답 문제 | `expect` · `why` · `tests.json` 의 `cases` |
| 연습용 · 시험용 | `set: dev` · `set: holdout` |
| 재확인 필요 | `label_current: false` · 화면의 `⚠` |
| 보류인데 가능 | `leaked_undetermined_as_feasible` |
| 비교 방식 | `arm` |
| LLM에 그냥 물음 · LLM에 '모르면 모른다' 지시 · LLM에 사실 데이터 줌 · 판정 코드 | `llm_naive` · `llm_only` · `llm_with_facts` · `code` |
| 사실 · 우리 기준 | `facts.json` · `policy.json` |
| 데이터 버전 | `snapshot_id` |
| 최소 이동시간 | `is_lower_bound: true` · `metro_ride_only` |
| 공식 페이지에서 옮김 · 공공데이터 · TMAP 실시간 조회 · 테스트용 가상 값 · 직접 측정 | `source`: `curated` · `public_data` · `api_runtime` · `synthetic_fixture` · `field_measured` |
| 말함 · 추정 · 없음 (날짜 · 시각을 어떻게 얻었나) | `date_source` · `start_source`: `explicit` · `inferred` · `missing` |
| 해결(사용자) · 해결(시스템) | `how_to_resolve`: `user` · `system` |
| 장소 | `stops[]` |
| 동네 | `scope: area` |

| 권장 여유 | `buffer_minutes` |
| 구간 | `legs` |

| 응답 캐시 | `response-cache.json` · 실행 기록의 `responses` |

### 여행 일정 쪽 말

| 말 | 뜻 |
| --- | --- |
| **장소** | 일정에 들어간 방문 장소 하나. `"1시 경복궁, 3시 광장시장"` 이면 장소 2곳 |
| **체류시간** | 그 장소에 머무는 시간. `"두 시간 볼 거예요"` 의 두 시간 |
| **입장마감** | **폐장 시각과 다른 값.** 경복궁 10월은 입장마감 17:00, 폐장 18:00 — 17:00 이후엔 들어갈 수 없다 |
| **개장 전 도착** | 불가능이 아니다. 기다렸다가 개장 시각에 들어간다고 보고, 체류와 다음 이동을 거기서부터 센다. 결과에는 안내만 붙는다 |
| **정기휴일** | 매주 쉬는 날. 경복궁은 화요일, 창덕궁·덕수궁은 월요일 |
| **고정 휴관일** | 매년 같은 날짜에 쉬는 날. 미술관 1월 1일. 요일 규칙과 따로 본다 |
| **대체공휴일** | 공휴일이 주말과 겹치면 평일 하루를 대신 쉬는 제도. 2026-10-05가 그렇다 |
| **필수 일정** | `"20:30 서울역 KTX는 꼭 타야 해요"` 처럼 사용자가 반드시 지킨다고 한 것. 열차 · 항공편 출발, 몇 시까지 도착 |
| **권장 여유** | **우리가 얹는 안전 여유.** 사실이 아니라 우리 기준이다. 구간 이동 10분, 열차 탑승 15분. 그래서 **위반을 가르는 데는 쓰지 않는다** — 권장 여유 때문에만 늦으면 `BUFFER_NOT_MET`(보류) |
| **구간** | 한 장소에서 다음 장소로 가는 이동 한 번 |
| **동네** | `"명동에서 쇼핑"` 처럼 여러 골목에 걸친 곳만 말한 경우. 어느 가게인지 몰라 운영시간을 볼 수 없으니 어디로 가는지 묻는다. 궁 · 시장 · 건물처럼 위치가 하나로 정해지는 곳은 동네가 아니라 장소다 |

### 이 프로그램의 세 부분

```
[구조화 추출]  자연어  →  구조        "10월 8일 목요일 오후 1시에 경복궁 두 시간"
                                       → { date: "2026-10-08", stops: [{place:"경복궁", start:"13:00", dwell_minutes:120}] }
               담당: LLM (extract.py)

[판정]         구조 + 사실 + 우리 기준  →  검사 결과
               담당: 판정 코드 (verdict.py)

[조회]         공휴일 · 지하철 데이터를 미리 받아 두고, TMAP 이동시간은 판정할 때만 받는다
               담당: fetch_holidays.py · build_transit_legs.py · routes.py
```

| 말 | 뜻 |
| --- | --- |
| **구조화 추출** | 말로 된 일정에서 날짜 · 장소 · 시각을 뽑아 정해진 틀(구조)에 채우는 단계. LLM을 한 번 불러 틀에 맞춘 답을 받는다(structured extraction). 입력에 없는 값은 채우지 않는다 |
| **판정** | 그 구조로 실행 가능성을 **검사하는** 단계 |
| **판정 코드** | 판정을 하는 코드(`verdict.py`). 외부 API를 부르지 않아서 같은 입력이면 늘 같은 답을 낸다 |
| **조회** | 외부에서 데이터를 받아 오는 부분(공휴일 · 지하철 · TMAP 길찾기). 판정 코드와 떼어 뒀다 |

## 1. 판정 결과를 읽을 때

### 검사 상태 — 통과 · 위반 · 미확인 · 해당 없음

검사 **하나**에 대한 결과다. 참/거짓 두 개가 아니라 네 개인 것이 이 프로젝트의 출발점이다.
결과 화면은 이 네 상태로 묶어 '확인한 것 · 어긋난 것 · 확인하지 못한 것 · 해당 없음'을 보여 준다.

| 상태 | 뜻 | 예시 |
| --- | --- | --- |
| 통과 | 근거를 **확보했고** 조건을 만족했다 | 경복궁 10월 입장마감 17:00 · 14:00 도착 |
| 위반 | 확보한 근거에서 위반이 **확인됐다** | 같은 근거 · 17:30 도착 |
| 미확인 | 검사가 **필요한데 끝내지 못했다** | 광장시장 영업시간을 확보하지 못했다 |
| 해당 없음 | 검사 **자체가 성립하지 않는다** | 휴무일로 확정된 곳의 운영시간 검사 |

**미확인과 해당 없음은 전혀 다르다.** 여기서 헷갈리면 서비스가 거짓말을 한다.

```
광장시장 영업시간을 모른다    →  검사는 필요하다. 끝내지 못했을 뿐  →  미확인
휴무일로 확정된 곳의 운영시간  →  검사가 필요 없다                  →  해당 없음
```

웹 접근성 검사기 axe-core 도 결과를 같은 네 갈래(passes · violations · incomplete · inapplicable)로 나눈다.

### 전체 판정 — 가능 · 불가능 · 보류

일정 **전체**에 대한 결과다. 검사 여러 개를 합쳐 **가장 나쁜 상태**로 정한다. 다수결이 아니다.

| 판정 | 조건 | 사용자에게 보여주는 문장 |
| --- | --- | --- |
| 불가능 | 위반이 **하나라도** 있다 | "확인한 정보에서 실행할 수 없는 부분이 발견되었습니다" |
| 보류 | 위반은 없지만 미확인이 있다 | "위반은 발견되지 않았지만 N개 항목을 확인하지 못했습니다" |
| 가능 | 필요한 검사가 **모두** 통과했다 | "확인한 정보와 검사 범위 내에서 위반이 발견되지 않았습니다" |

**가능일 때도 "실행 가능한 일정입니다" 라고 말하지 않는다.** 예약·날씨·혼잡도는 검사 범위 밖이라 보장할 수 없는 말이다.

### 보류인데 가능 — 가장 나쁜 오류

> **정답이 보류(확인 못 했다)인데 가능(문제 없다)으로 답한 경우**

**이 프로젝트가 막으려는 단 하나의 실패다.** 실행 기록에는 `leaked_undetermined_as_feasible` 로 남는다.

```
T14  "2027년 3월 5일 금요일 오후 1시에 경복궁 두 시간 보려고요."

     우리가 가진 근거 — 경복궁 운영시간. 단 2026년 기준이고 2026-12-31 까지 유효
     방문일이 2027년 → 이 근거를 쓸 수 없다 → 2027년에 몇 시에 여는지 모른다

     정답                  보류   "확인 못 했습니다"
     LLM에 그냥 물은 답     가능   "문제 없습니다"      ← 보류인데 가능
```

> 9월 22일 claude-opus-5 실행의 답이다. 10월 2일 claude-opus-5-5 실행에서는 T14를 보류했고,
> 대신 T03 · T08 · T13을 가능이라고 했다. 어느 케이스에서 새는지는 실행마다 바뀐다.

**틀린 답보다 나쁘다.**

```
"확인 못 했습니다"  →  사용자가 직접 경복궁 홈페이지를 본다
"문제 없습니다"     →  사용자가 그냥 간다
```

그래서 `run.py` 요약에 이렇게 박아뒀다 — `보류인데 가능으로 낸 건수 (0이 아니면 다른 지표를 볼 필요가 없다)`.
정확도가 99%여도 이게 1건 있으면 검증 서비스로는 실패다.

### 심각도 — 치명 · 주의

검사 상태와 **다른 질문**이다.

| | 묻는 것 |
| --- | --- |
| 검사 상태 | 지금 정보로 **확정할 수 있나** |
| 심각도 | 실패하면 **타격이 큰가** |

KTX를 놓치는 건 정보가 부족해도 여전히 치명적이다. 그래서 미확인이라고 심각도를 낮추지 않는다. 낮추면 "중요도 낮음" 으로 보여서 사용자가 확인을 건너뛴다.

### 보류 이유 (`unknown_reason`) — 왜 못 끝냈나

같은 미확인이라도 **해결 방법이 다르므로** 따로 적는다. 이유 이름은 코드 값 그대로 둔다.

| 이유 | 뜻 | 어떻게 해결하나 |
| --- | --- | --- |
| `NO_CLOSED_DAY_DATA` | 휴무일 정보를 못 구했다 | 데이터 확보 |
| `NO_OPERATING_HOURS_DATA` | 운영시간을 못 구했다 | 데이터 확보 |
| `EVIDENCE_EXPIRED` | 근거의 적용 기간이 지났다 | 다시 확인 |
| `PLACE_NOT_RESOLVED` | 동네만 말해서 방문할 시설이나 가게를 특정하지 못했다 | 사용자에게 어디로 가는지 묻는다 |
| `UNSUPPORTED_PLACE` | 지원하는 장소 목록에 없어 확인하지 않았다 | 장소 정보를 확보한다. 사용자에게 묻지 않는다 |
| `HOLIDAY_CALENDAR_UNVERIFIED` | 공휴일 달력을 아직 확인하지 않았다 | API 호출 |
| `UNVERIFIED_TRAVEL_TIME` | 그 구간 이동시간이 없다 | 데이터 확보 |
| `LOWER_BOUND_ONLY` | 최소 이동시간밖에 없다 | 걷기·환승·대기 시간 확보 |
| `NO_USER_DWELL` | 사용자가 체류시간을 안 말했다 | 사용자에게 물어본다 |
| `LATE_BY_LOWER_BOUND` | 지하철 **최소 이동시간**으로도 늦는다. 택시 등 다른 수단은 확인하지 못했다 | 사용자에게 알리고 일정 조정을 묻는다 |
| `LATE_BY_ESTIMATE` | 길찾기 **예상 이동시간**으로는 늦는다. 예상치라 확정하지 않는다 | 사용자에게 알리고 일정 조정을 묻는다 |
| `INFERRED_INPUT` | LLM 이 **추정한 입력**(시각, 요일 없이 채운 연도)으로만 나온 결과다 | 사용자에게 확인한다 |
| `BUFFER_NOT_MET` | 제시간에 닿지만 **권장 여유에 못 미친다** | 사용자에게 알리고 판단을 맡긴다 |
| `NO_BUFFER_RULE` | 필수 일정에 둘 **권장 여유 기준이 없다** — 항공편 탑승 수속 · 보안 검색 | 사용자에게 알리고, 공식 안내를 확보한다 |
| `RULE_CONFLICT` | 공식 문구 두 개가 **반대 결론**을 낸다 (미술관 1월 1일이 월요일인 해) | 기관에 확인 |
| `MIDDAY_HARD_CONSTRAINT` | 필수 일정이 **하루 중간**에 있다. 아직 하루 마지막 교통편만 판정한다. 그 일정을 사이에 둔 두 장소의 이동도 같은 이유로 미확인이다 | 검사를 만든다. 그때까지는 사용자에게 알린다 |
| `DWELL_BEYOND_TOUR` | 회차 입장 날에 말한 체류가 **해설 관람(50분 정도)보다 길다** | 사용자에게 해설 시간 안으로 잡아도 되는지 묻는다 |
| `AT_LAST_ADMISSION` | **입장마감 정각**에 도착한다. 공식 안내가 정각에 들어가는지 말하지 않는다 | 사용자에게 조금 일찍 도착할 수 있는지 묻는다 |
| `UNVERIFIED_ALWAYS_OPEN` | 상시 개방이라는 공식 근거를 확보하지 않았다 | 공식 출처 확인 |
| `MISSING_DATE` · `INVALID_DATE` | 방문 날짜가 없거나 `YYYY-MM-DD`로 못 읽는다 | 사용자에게 물어본다 |
| `MISSING_STOPS` · `MISSING_PLACE` | 방문할 장소가 없다 | 사용자에게 물어본다 |
| `MISSING_START_TIME` | 방문 시작 시각이 없다. 그 장소의 휴무일은 날짜로 확인하고, 입장 · 체류와 앞뒤 이동을 이 이유로 묻는다 | 사용자에게 물어본다 |
| `INVALID_TIME` | 시각을 `HH:MM`(24시간)으로 못 읽는다 (`"1:00 PM"`) | 사용자에게 물어본다 |
| `INCOMPLETE_HARD_CONSTRAINT` | 필수 일정에 장소 또는 시각이 빠졌다. 필수 일정은 결과에 그대로 남긴다 | 사용자에게 물어본다 |
| `MISMATCHED_WEEKDAY` | 날짜와 요일이 서로 맞지 않는다. 어느 날을 뜻했는지 모른다 | 사용자에게 어느 날인지 물어본다 |

## 2. 데이터를 볼 때

### 사실과 우리 기준

**두 파일로 나눠놓은 이유가 있다.**

| | 사실 (`facts.json`) | 우리 기준 (`policy.json`) |
| --- | --- | --- |
| 뭐가 들어가나 | 운영시간·휴무일·이동시간·공휴일 | 기본 체류시간·권장 여유·판정 기준 |
| 출처 | 공식 페이지 · 공공데이터 | **우리가 정한 값. 출처 URL이 없다** |
| 바뀌면 | 세상이 바뀐 것 | 우리 생각이 바뀐 것 |

한 파일에 두면 판정 결과를 보고 **"이게 공식 정보인가 우리가 정한 값인가"** 를 구분할 수 없다.

`policy.json` 첫 줄에 이렇게 적어뒀다 — *"전부 우리가 정한 값이다. 출처 URL이 없다. 사실이 아니라 설정이다."*

지금 우리 기준:

| | 값 | 뜻 |
| --- | --- | --- |
| `default_dwell_minutes` | 궁궐 90 · 미술관 60 · 시장식사 60 · 거리 45 | 체류시간을 안 말했을 때 **안내에만** 쓰는 기본값. 판정에는 쓰지 않는다 |
| `buffer_minutes.transit_leg` | 10분 | 구간 이동에 두는 여유 |
| `buffer_minutes.rail_boarding` | 15분 | 열차 탑승 전 권장 도착 여유 |
| `require_user_dwell_for_completion_check` | true | 체류시간을 안 말했으면 체류 검사를 안 한다 |

### 근거

값 하나에 붙는 출처 정보다. **값만 있으면 근거가 아니다.**

| 필드 | 뜻 | 없으면 |
| --- | --- | --- |
| `source` | 어디서 왔나 (아래 표) | 저장소에 넣어도 되는지 판단 못 함 |
| `url` | 원 페이지 주소 | 다시 확인할 수 없음 |
| `checked_at` | 언제 확인했나 | 얼마나 오래된 값인지 모름 |
| **`valid_until`** | **언제까지 쓸 수 있나** | 작년 시간표로 올해를 판정함 |
| `rule_text` | 공식 안내 문구 원문 | 페이지가 바뀌었을 때 비교 기준이 없음 |
| `verified_by` | 확인 방법 | 정말 확인했는지 알 수 없음 |

**출처**로 *"저장소에 저장해도 되는가"* 를 판단한다.

| 출처 | 코드 값 | 뜻 | 저장 |
| --- | --- | --- | --- |
| 공식 페이지에서 옮김 | `curated` | **사람이 공식 페이지를 읽고 옮긴 것.** 국가유산청·서울시립미술관 | ✅ |
| 공공데이터 | `public_data` | 공공누리 1유형 또는 이용허락범위 제한 없음 | ✅ |
| 직접 측정 | `field_measured` | 사람이 실제로 이동해서 잰 값. 데이터 정책에 허용된 출처로만 적어 뒀고 지금 쓰는 데이터는 없다 | ✅ |
| TMAP 실시간 조회 | `api_runtime` | 판정할 때 받은 상업 API 응답. 화면에만 쓰고 버린다 | ❌ 약관상 불가 |
| 테스트용 가상 값 | `synthetic_fixture` | 정답 문제에만 쓰는, 실제가 아닌 이동시간 | 테스트에서만 |

'공식 페이지에서 옮김'은 사람이 손으로 넣었다는 뜻이라 엉성하게 들리지만, **오히려 가장 믿을 수 있는 출처**다.
공식 페이지 문구를 그대로 옮기고 URL·확인일·확인 방법을 함께 남기기 때문이다.
상업 API는 값이 자동으로 오는 대신 입장마감·계절별 시간표 같은 필드가 아예 없다.

### 적용 기간 (`valid_until`)

> 오늘 조회했다는 사실만으로 다음 달 방문일에 쓸 수 있는 정보가 되지는 않는다.

T14가 이걸 검사한다. 경복궁 운영시간은 2026년 안내 기준이고 `valid_until: 2026-12-31` 이다. 2027년 방문일에는 **근거가 있어도 쓸 수 없다.**

Google Places 응답에는 이 개념이 **아예 없다.**

### 데이터 버전 (`snapshot_id`)

사실 데이터(`facts.json`) 전체의 **버전**이다. 지금은 `facts-2026-09-29`.

데이터가 바뀌면 이 값을 올린다. 그래야 *"이 판정 결과는 어느 데이터로 나온 것인가"* 를 되짚을 수 있다.

`snapshot_history` 에 버전별로 무엇이 바뀌었는지 남긴다. 그게 **정답 재확인 필요**를 찾아내는 근거가 된다 (아래 참조).

### 최소 이동시간

**실제 이동시간보다 짧다는 것이 보장된 값.** 수학에서 말하는 하한(lower bound)이다.

저장해 둔 이동시간은 **4개 구간뿐**이고, 그것도 지하철 **탑승 시간**뿐이다.
나머지 구간은 저장한 값이 없다. 판정할 때 TMAP으로 받고(`core/verify.py`), TMAP 없이 돌리면 `UNVERIFIED_TRAVEL_TIME`이다.

탑승 시간은 역 사이 표준 운행시간 — *"열차가 출발하여 다음역에 도착하는"* 시간 — 을 이어 더한 값이다. 빠진 것 —

```
장소 → 역 걷기          없음
환승 이동시간          없음
열차 대기시간(배차)    없음
중간역 정차시간        없음
```

중간역 정차시간은 출처에 **명시가 없다.** 포함 여부를 원문으로 확인하지 못해서 수치로 대조했다 —
2호선 순환(시청→시청, 43개 역간)을 이 데이터로 더하면 **65분**인데, 표준 운행시간은 **87\~90분**이다.
차이를 역 수로 나누면 역당 30초 남짓으로, 정차시간 크기와 맞는다. 그래서 빠진 것으로 본다.

| 구간 | 최소 이동시간 |
| --- | --- |
| 미술관 → 경복궁 | 6.5분 (환승 1회) |
| 경복궁 → 미술관 | 6.5분 (환승 1회) |
| 경복궁 → 광장시장 | 4.5분 (환승 1회) |
| 광장시장 → 서울역 | 7.0분 (환승 0회) |

데이터 범위도 좁다. 서울교통공사 1\~8호선만 있고, 1호선은 서울역\~청량리 구간뿐이다.

빠진 몫이 얼마인지는 **모른다.** 그래도 말할 수 있는 것이 있다.
크기를 몰라도 부호를 알기 때문이다 — 빠진 값은 언제나 0보다 크다.

**최소 이동시간은 한 방향으로만 말해 준다.**

```
최소 이동시간으로도 늦는다    →  지하철로는 확실히 늦다   빠진 값을 더하면 더 늦어질 뿐이다
최소 이동시간으로는 도착한다  →  확정할 수 없다           나머지를 모른다
```

**이 값은 지하철로 갈 때의 최소다.** 택시로는 더 빨리 갈 수도 있다. 이 서비스는 사용자가 고른
이동수단을 보지 않고, 되는 수단이 하나라도 있으면 된다고 본다(2026-10-05 결정). 그래서 최소 이동시간으로도
늦으면 위반이 아니라 `LATE_BY_LOWER_BOUND`(보류)로 두고, 지하철로는 늦는다고 알린 뒤 일정 조정을 묻는다.

```
미술관 13:00 에 한 시간, 경복궁 14:05   지하철로는 14:06 도착
  →  미확인   "지하철로는 경복궁에 늦어요. 시작을 늦추거나 더 일찍 출발할 수 있나요?"
```

예외는 **이동시간이 0분이어도 늦는** 경우다. 미술관 13:00 에 한 시간 보고 경복궁 13:50 이면
순간이동을 해도 못 간다. 이건 수단과 상관없이 위반이다.

### 최소 체류 0분

사용자가 체류시간을 말하지 않았으면 **기본값으로 판정하지 않는다.** 체류 검사(T08)와 같은 원칙이다.

위반은 *"어떻게 머물든 늦는다"* 의 증명이어야 한다. 체류시간은 0보다 작을 수 없으므로 **0분이 보장된 최소**다.

```
체류를 모를 때
  0분으로도 늦는다   →  늦는다     더 머물면 더 늦어질 뿐이다
  0분이면 도착한다   →  미확인     얼마나 머물지 모르니 확정할 수 없다 → 사용자에게 묻는다
```

최소 이동시간과 같은 모양이다. 이동은 탑승 시간이, 체류는 0분이 보장된 최솟값이다.
다만 '늦는다'를 위반으로 확정하는 건 이동까지 0분으로 봐도 늦을 때뿐이다. 이동시간이 지하철 최소 이동시간이나
길찾기 예상치면 다른 수단으로는 닿을 수 있어 미확인(`LATE_BY_LOWER_BOUND` · `LATE_BY_ESTIMATE`)으로 둔다.

```
T12  "10월 8일 목요일 오후 1시에 경복궁 보고 3시 15분에 광장시장 갈게요."

     체류시간을 안 말했다
       0분이면 13:04 도착   →  늦는다고 할 수 없다
       얼마나 머물지 모른다  →  도착한다고도 할 수 없다
                             →  미확인 (NO_USER_DWELL)
```

기본값(궁궐 90분)은 판정에 쓰지 않고 **안내에만** 쓴다. 경복궁 10:00 → 광장시장 10:30 이면
*"기본값 90분으로 보면 11:34 도착이라 늦을 수 있다"* 를 붙여 사용자에게 체류시간을 묻는다.

전에는 기본값을 ±50% 흔들어(45분·135분) 두 결과가 같으면 그대로 확정했다. 하지만 그 범위는
**우리 추측을 중심으로 한 범위**일 뿐이다. 20분만 둘러보는 사람도 있다. 45분으로도 늦는다는
이유로 위반을 내면, 우리가 정한 값으로 사용자 일정의 오류를 만들어내게 된다.

### 추정한 입력 (`inferred`)

구조화 추출 단계(LLM)가 입력에 없는 값을 **짐작해서 채운** 것이다. 두 가지가 있다.

```
시작 시각   "점심 먹고 경복궁"  →  12:00        start_source = inferred
시작 시각   "4시에 공원"        →  16:00        start_source = inferred   오전·오후도, 기댈 앞 시각도 없다
연도       "10월 6일"          →  2026-10-06   date_source  = inferred
```

추정한 값에 기대는 결과는 **통과든 위반이든 확정하지 않는다** (`INFERRED_INPUT`).
추정한 12:00 으로 "입장 불가" 를 내면 짐작으로 불가능을 단정한 것이고, "입장 가능" 을 내도
짐작으로 가능을 단정한 것이다. 계산 결과는 참고로 남기고 *"경복궁에 12:00에 도착하는 것이
맞나요?"* 를 묻는다. 기본 체류시간과 같은 원칙이다.

연도는 요일로 확인할 수 있다. *"10월 6일 화요일"* 처럼 말한 요일이 채운 날짜와 맞으면 날짜는
사용자 말로 확인된 것이다. 요일 없이 연도만 채웠을 때만 추정으로 본다.

### 회차 입장 (`timed_entry`) / 상시 개방 (`always_open`)

| | 뜻 | 지금 상태 |
| --- | --- | --- |
| 회차 입장 | 정해진 시각에만 입장 (종묘 월·목·금, 해설사 동반 50분 정도) | 도착 뒤 첫 한국어 회차에 들어간다. 마지막 회차 뒤 도착은 위반 |
| 상시 개방 | 운영시간 개념이 없음 (청계천·덕수궁 돌담길) | 근거 미확보 → `UNVERIFIED_ALWAYS_OPEN` |

상시 개방을 '해당 없음'(검사 필요 없음)으로 두고 싶지만, **상시 개방임을 확인하지 않았으면 그것도 추측이다.** 확인 전에는 미확인이다.

## 3. 정답 문제를 볼 때

### 정답 문제와 정답

| | 뜻 |
| --- | --- |
| **정답 문제** | 사람이 공식 근거를 보고 정답을 미리 적어 둔 문제 모음. 지금 29개(`tests.json`). 소프트웨어 테스트에서 골든 테스트라고 부르는 것 |
| **정답** | 그 문제의 기대 판정과 이유. `tests.json` 의 `expect` 와 `why` |

**정답을 만들 때 판정 코드를 보지 않는다.** 코드로 정답을 만들고 그 코드가 맞혔다고 평가하면 규칙의 오류를 영원히 발견할 수 없다.

문제 하나에 들어가는 것:

| 필드 | 내용 |
| --- | --- |
| `raw` | 입력 자연어 원문 |
| `date` · `date_source` · `weekday_stated` · `stops` · `hard_constraints` | **기대 추출값** — LLM이 이렇게 추출해야 한다 |
| `expect_applied` | 적용해야 하는 사실·가정·빠진 정보 |
| `expect` · `expect_checks` | **기대 판정** |
| `why` | 왜 그 판정인지 (정답의 근거) |
| `legs` | (있을 때만) 문제별 테스트용 가상 이동시간. 실제 값이 아니다 |

### 연습용과 시험용

| | 코드 값 | 뜻 |
| --- | --- | --- |
| 연습용 | `set: dev` | 코드를 만들면서 계속 돌려 보고, 틀리면 코드를 고친 문제. 9건 |
| 시험용 | `set: holdout` | 정답을 먼저 적어 커밋해 두고, **코드를 이 문제들에 맞춰 고치지 않은** 문제. 24건 |

공부할 때 연습 문제로 익히고 시험은 처음 보는 문제로 보는 것과 같다. 연습 문제를 다 맞혔다는 것은 문제에 맞춰 고쳤으니
실력의 증거가 약하고, 처음 보는 문제를 맞힌 것이 진짜 증거다. 머신러닝 평가에서 dev set · held-out set 이라고 부르는 나눔이다.
다만 **T01\~T15는 전부 결과를 본 상태**라, 2026-10-06 · 10-07 · 10-14에 결과를 보지 않은 시험용 18건(T16\~T33)을 새로 만들고
처음 돌리기 전에 정답부터 커밋했다.

### 정답 재확인 필요

> **같은 입력인데 데이터가 바뀌어서 정답이 달라졌을 수 있는 상태**

정답은 판정 코드와 독립이어야 하지만 **데이터 버전과는 독립일 수 없다.**

```
T10  "10월 8일 목요일 오후 2시에 창덕궁 한 시간 반 보려고요."   ← 입력은 안 바뀜

     전   정답 보류   "창덕궁 관람시간을 확보하지 못했다"
          ↓  창덕궁 관람시간을 공식 페이지에서 확보함
     후   정답 가능   09:00~18:00, 입장마감 17:00 → 14:00 도착 OK
```

**이걸 방치하면 핵심 지표가 거짓 경보를 낸다.** 실제로 '보류인데 가능' 1건이 떴는데, 코드 버그가 아니라 정답이 옛 데이터 기준이었다.

그래서 자동으로 찾아낸다(`core/labels.py`, `run.py` · `run_extract.py` · `compare.py` 가 같이 쓴다). 정답을 검토한 뒤의
데이터 변경을 **모두** 보고, 그중 **문제가 기대는 데이터가 바뀐 것이 있을 때만** 재확인 필요로 본다.

| 표시 | 뜻 |
| --- | --- |
| `✅` | 검토된 정답과 일치 |
| `❌` | 검토된 정답과 불일치 — **실제 문제** |
| `⚠ 재확인 필요(일치)` | 재확인이 필요한 정답과 맞았을 뿐 |
| `⚠ 재확인 필요(불일치)` | 데이터가 바뀌어 정답이 달라졌을 가능성 |

> 판단할 때 **판정 코드의 출력을 보지 않는다.** "코드 출력이 정답과 다르면 정답이 낡은 것" 으로
> 하면 코드에 진짜 버그가 있을 때도 넘어가 버린다. 문제의 장소 목록과 바뀐 키 목록,
> **데이터끼리만** 비교한다.

---

## 4. 비교 실험을 볼 때

### 비교 방식

**견주는 판정 방법 하나하나.** 의학 임상시험의 대조군 · 실험군처럼 한 번에 하나만 바꿔 가며 견준다(영어로는 arm).

판정 코드만 돌려서 다 맞았다고 해도, 그게 데이터를 잘 모아서인지 규칙을 잘 짜서인지 아니면 LLM에게 그냥 물어봐도 됐을 일인지
알 수 없다. 그래서 **한 번에 하나씩만 바꿔 가며** 비교한다.

| 비교 방식 | 코드 값 | 무엇을 주나 | 판정하는 쪽 |
| --- | --- | --- | --- |
| LLM에 그냥 물음 | `llm_naive` | 자연어 일정만 | LLM · **아무 지시 없음** |
| LLM에 '모르면 모른다' 지시 | `llm_only` | **같은** 자연어 일정만 | LLM · "근거 없으면 모른다고 해라" **지시 추가** |
| LLM에 사실 데이터 줌 | `llm_with_facts` | 구조화한 일정 + 사실 + 우리 기준 | LLM |
| 판정 코드 | `code` | **같은 것** | `verdict.py` |

```
그냥 물음          →  '모르면 모른다' 지시   지시만 추가       →  지시의 효과
'모르면 모른다'    →  사실 데이터 줌         데이터만 추가     →  데이터의 효과
사실 데이터 줌     →  판정 코드              판정 주체만 교체  →  코드의 효과
```

### 지표

정답과 답이 다른 경우는 **"정답은 무엇인데 무엇이라고 답했나"** 짝으로 부른다. 외울 이름 없이 그대로 읽힌다.
분류 모델을 평가할 때 쓰는 혼동행렬(정답 × 답 표)의 칸 이름과 같은 방식이다.

| 지표 | 뜻 | 왜 보나 |
| --- | --- | --- |
| **전체 정확도** | 전체 중 몇 건 맞췄나 | 기본 |
| **정밀도** | '불가능'이라고 **답한 것 중** 정답도 불가능인 비율 | 헛경보를 얼마나 내나 |
| **재현율** | 정답이 불가능인 것 **중** 불가능이라고 잡아낸 비율 | 얼마나 놓치나 |
| **보류인데 가능** | 확인하지 못한 일정을 괜찮다고 했다 | **가장 위험하다** — 사용자가 확인 없이 그냥 간다 |
| **불가능인데 가능** | 안 되는 일정을 괜찮다고 했다 | 위험하다 — 확정된 위반을 놓쳤다 |
| 가능인데 불가능 | 멀쩡한 일정을 막았다 | 헛경보 |
| 보류인데 불가능 | 근거 없이 불가능이라고 단정했다 | 추측으로 막았다 |
| 불가능인데 보류 | 확정할 수 있는 위반을 보류로 덮었다 | 덜 알려 줬다 |
| 가능인데 보류 | 확인할 수 있는데도 답을 안 줬다 | 덜 알려 줬다 |
| **보류 비율** | 보류를 낸 비율 | 얼마나 자주 답을 못 주나 |
| **답을 준 비율** | 보류가 **아닌** 답을 준 비율 | 쓸모가 있나 |

**정밀도와 재현율은 헷갈리기 쉽다.** 분모가 다르다.

```
정답이 불가능인 일정이 6건 있다. 검증기가 5건을 "불가능" 이라고 했고 그 5건이 다 맞았다면

  정밀도 = 5 / 5 = 1.0     분모는 "내가 불가능이라고 한 것"   → 헛소리를 안 했다
  재현율 = 5 / 6 = 0.833   분모는 "정답이 불가능인 것 전체"   → 1건을 놓쳤다
```

9월 22일 실행의 'LLM에 그냥 물음'이 정확히 이 숫자였다 — 불가능이라고 한 건 전부 맞았지만(정밀도 1.0) 1건을 놓쳤다(재현율 0.833).
10월 2일 실행에서는 불가능이라고 한 2건은 맞았지만 나머지 4건을 보류해서 재현율이 0.333이었다.
10월 12일에 받은 응답(29건)에서는 불가능이라고 한 8건 중 7건이 맞아 정밀도 0.875, 정답이 불가능인 10건 중 7건을 찾아 재현율 0.7이었다.

**보류 비율과 답을 준 비율을 같이 봐야 하는 이유** —

모든 일정을 보류로 내는 검증기는 '보류인데 가능' 0, '가능인데 불가능' 0으로 **지표가 완벽해 보인다.** 그런데 사용자는
아무 답도 받지 못한다. 실제로 'LLM에 모르면 모른다 지시'가 그랬다 — 10월 2일 기록에서 15건을 전부 보류했다.
아래는 10월 12일에 받은 응답(29건)이다.

| 비교 방식 | 보류인데 가능 | 답을 준 비율 | |
| --- | --- | --- | --- |
| LLM에 그냥 물음 | 12 | 0.862 | 답은 많이 하지만 근거 없는 답이 섞여 있다 |
| LLM에 '모르면 모른다' 지시 | 1 | 0.103 | 거의 답하지 않는데도 확인 못 한 걸 괜찮다고 한 적이 있다 |
| LLM에 사실 데이터 줌 | 1 | 0.552 | |
| 판정 코드 | **0** | **0.552** | **틀린 확신 없이 답을 준다** |

### 표본이 작을 때 조심할 것

지금 33건이다. 정답 분포는 불가능 11 · 가능 8 · 보류 14.

| | 읽을 수 있나 |
| --- | --- |
| 정밀도 · 재현율 | ⚠️ 분모가 11이라 1건 차이가 약 9%p를 움직인다 |
| 가능인데 불가능 | ⚠️ 분모가 가능 8건이라 아직 약하다 |
| **보류인데 가능** | ✅ **"있다" 를 확정하는 쪽이라 표본이 작아도 유효하다** |
| 보류 비율 · 답을 준 비율 | ✅ 비율로 읽을 수 있다 |

> 실제로 이걸 틀린 적이 있다. 7건만 채점했던 중간 결과에서 'LLM에 그냥 물음'과 판정 코드의 보류 비율이
> 둘 다 0.286으로 나왔다. 그래서 **"판단한 양이 같은데 코드가 더 정확하다"** 고 읽었다.
> 그런데 15건으로 채점하니(9월 22일) **0.133 대 0.467** 로 전혀 달랐다 — 그때 'LLM에 그냥 물음'은 훨씬 많이 답했다.
> 표본이 작을 때 비율을 해석하면 이런 일이 생긴다.

### 응답 캐시 — 같은 요청이면 다시 부르지 않는다

LLM을 부르면 돈이 든다. 그래서 평가 실행은 받은 응답을 저장해 두고(`core/response-cache.json`), 모델에 보낼 내용이
같으면 다시 부르지 않고 그 응답을 쓴다. 캐시(cache)는 한 번 얻은 결과를 다시 쓰려고 넣어 두는 곳을 가리키는 말이다.

```
같은 요청     모델 · 프롬프트 · 본문 · 출력 형식이 모두 같다   → 받아 둔 응답을 쓴다. 비용 $0
다른 요청     프롬프트나 사실 데이터가 한 글자라도 바뀌었다     → 그 요청만 새로 부른다
```

화면 글만 바꾼 커밋 뒤에도 기록을 다시 만들 수 있는 이유가 이것이다. 채점과 판정은 지금 코드로 다시 하고, LLM 응답만
받아 둔 것을 쓴다. 새로 부를 호출이 있으면 몇 건이고 얼마쯤 드는지 먼저 보여 주고 `y`를 받는다.

> 받아 둔 응답을 다시 쓰는 실행은 LLM이 같은 입력에 답을 바꾸는지 보여 주지 않는다. 그걸 보려면 `--fresh`로 새로 받는다.
> 토큰 사용량에 나오는 '프롬프트 캐시'는 다른 것이다 — Anthropic 쪽에서 같은 시스템 프롬프트를 싸게 다시 읽게 해 주는 기능이다.
