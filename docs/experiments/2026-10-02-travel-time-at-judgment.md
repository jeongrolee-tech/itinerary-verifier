# 261002 — 이동시간을 판정할 때 조회하기로

**입력 조건** 코드 f6c50c1 로 만든 판정 기록(`core/last-run.json`, 커밋 75326c0),
`facts.json` 의 이동 구간 4개(전부 지하철 주행시간 하한선), 공공데이터와 길찾기 API 약관 조사(2026-10-02).

## 관찰 결과

- 이동 구간 4개가 전부 하한선이라 이동 검사는 `pass` 가 나오지 않는다.
  장소가 둘 이상인 일정은 다른 검사가 다 통과해도 `undetermined` 다
- T01 은 미술관에서 14:00 에 나와 15:00 까지 경복궁에 가면 된다. 주행시간 6.5분에 권장 여유 10분을
  더해도 44분이 남는데 `LOWER_BOUND_ONLY` 로 보류했다
- 09-22 커밋 6b839b8 에 이미 적혀 있었다. 주행시간은 Google 문전 이동시간의 15~27% 였고,
  나머지 73~85%(도보·환승·대기)는 근거가 없었다
- 같은 날 [`docs/data-policy.md`](../data-policy.md) 는 "런타임에 호출해서 판정에 사용" 을 허용되는 용도로
  적었다. 그런데 그 조회 계층은 만들지 않았다

- 열차 대기 — 서울교통공사 열차운행시각표(공공데이터포털 15098251). 1~9호선, 평일 · 토요일 · 휴일
- 환승 — 서울교통공사 환승역거리 소요시간(15044419). 145개역, 최단 환승거리 ÷ 1.2m/s
- 장소 ↔ 역 도보 — 서울시 도보 네트워크(15125685)는 있다. 출입구 좌표는 확인하지 못했고,
  출입구에서 승강장까지의 시간은 찾지 못했다
- 길찾기 API — Google · 카카오 · 네이버 · ODsay · TMAP 모두 결과 저장을 금지한다

## 해석

- 상한선을 직접 만드는 것은 길찾기 엔진을 작게 다시 만드는 일이다. 걷는 속도를 우리가 정해야 하고,
  미리 계산한 구간에서만 통한다. 장소가 하나 늘 때마다 구간 데이터를 또 만들어야 한다
- 길찾기 API 가 이미 그 일을 한다. 약관이 막는 것은 저장이지 사용이 아니다
- 플랫폼은 처음에 이미 키가 있는 Google 로 하려 했다. 그런데 Google 은 한국에서 대중교통 경로만 준다(09-13 실험).
  다섯 곳을 비교해 보니(README '길찾기 플랫폼별로 되는 것') TMAP 하나로 대중교통 · 걷기 · 자동차가 되고,
  대중교통은 출발 시각(`searchDttm`)도 정할 수 있었다
- 문서만 믿지 않고 TMAP 을 직접 불러 확인했다(`check-tmap-api.mjs`, 2026-10-02). 대중교통 4구간 중 3구간에서
  경로가 왔고, 2027-03-05 출발도 됐다. 아주 가까운 구간(덕수궁 → 미술관)은 HTTP 200 에 코드 11
  "출발지와 도착지가 너무 가까움" 으로 결과가 없었다. 걷기 2구간과 자동차 1구간(택시 요금 포함)은 모두 왔다.
  받은 시간과 요금은 약관상 적지 않는다

## 결정

- 실제로 쓸 때 — 판정하는 순간 TMAP 으로 조회하고 저장하지 않는다
- 테스트할 때 — 판정 규칙은 우리가 정한 이동시간으로, 골든 테스트와 비교 실험은 저장해 둔 하한선으로 돌린다
- 예상 이동시간으로만 늦으면 `infeasible` 을 확정하지 않는다. 확정은 이동 0분이나 지하철 하한선으로만 한다
- 대중교통이 너무 가깝다고 하면(코드 11) 걷기 경로로 판정한다
- 걷기와 택시는 TMAP 보행자 · 자동차 경로로, 사용자가 그 수단을 말했을 때 쓴다
