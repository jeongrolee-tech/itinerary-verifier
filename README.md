# itinerary-verifier

여행 일정이 실제로 실행 가능한지 검증한다. **확인한 것 / 어긋난 것 / 확인하지 못한 것**을 근거와 함께 나눠서 낸다.

> Checks whether a travel itinerary is actually executable — validates opening hours,
> closures and transit times against official sources, and **reports what it could not verify**.

**다루는 범위** — 서울 · 당일 · 스톱 3~6개 · 대중교통 기본.
제외 — 해외 도시 / 1박 이상 / 예약 / 예산 / 날씨 / 동선 최적화 / 다국어 / 자동차

> **용어가 낯설면** [`docs/용어.md`](docs/용어.md) 를 먼저 보면 된다.
> `누출` · `하한선` · `arm` · `라벨 노후화` 처럼 이 프로젝트가 정한 말을 예시와 함께 정리해뒀다.

## 왜 만들었나

여행 전에 일정을 확정하는 데 생각보다 시간이 오래 걸린다는 것을 여러 번 겪었다.
갈 곳마다 공식 페이지를 찾아 휴무일과 운영시간을 확인하고, 블로그와 유튜브에서
"월요일 휴관이래요" 같은 정보를 우연히 건진다. 그렇게 확정해도 현장에서 틀어질지는
끝까지 알 수 없다.

계획은 몇 주 전에 시작하더라도, **검증이 의미를 갖는 것은 방문일에 가까울수록**이다.
운영시간과 휴무일은 바뀌기 때문이다. 그래서 모든 근거에 유효기간을 붙여두고, 방문일이
그 기간을 벗어나면 판정하지 않는다 — 몇 달 뒤 일정을 지금 근거로 "괜찮다"고 말하지
않는다. 언제 쓰든 사전에 찾은 오류는 고칠 수 있지만, 현장에서 찾으면 그냥 손해다.

진짜 문제는 **처음 가는 도시**다. 아는 것이 없으니 확인할 것도 많다. 그런데 검증기를
만들려면 라벨을 판정 코드가 아니라 **공식 페이지 문구에서** 만들어야 하고, 그러려면
내가 그 출처를 직접 읽을 수 있어야 한다. 그래서 **서울로 좁혔다.** 범위를 줄인 것이
아니라 검증이 성립하는 범위를 고른 것이다.

그래서 이걸 LLM에 맡기면 어디까지 되나. 그게 이 프로젝트의 질문이었고,
답은 [비교 실험](#비교-실험-claude-opus-5-effort-low-15건)에 있다 — **맡기면 안 되는 단계가 있었다.**
LLM은 자연어를 구조로 옮기는 데만 쓰고, 근거가 충분한지와 실행 가능한지는 코드가 판정한다.

## 무엇이 다른가

오류를 못 찾은 것과 문제가 없는 것은 다르다. 이 검증기는 근거를 확보하지 못하면 `pass`를 내지 않는다.

```
verdict = infeasible      확인된 위반이 있다
          undetermined    위반은 없지만 필수 검사가 미확인이다
          feasible        필요한 검사가 모두 통과했다
```

사용자에게도 "실행 가능한 일정입니다"가 아니라 **"확인한 정보와 검사 범위 내에서 위반이 발견되지 않았습니다"**라고 말한다.

## 돌려보기

키 없이 바로 된다. 자연어 일정을 넣으면 검사별로 무엇을 확인했고 무엇을 못 했는지 나온다.
판정 3종이 각각 어떻게 생겼는지 아래 셋으로 보면 된다.

### `undetermined` — 근거가 없어서 판단하지 않는다

```bash
python core/run.py --case T08
```

```
입력: 10월 8일 목요일 오후 4시 반에 경복궁 갈게요.

[추출]
  16:30  경복궁  체류 미입력

[적용한 기본값]
  A1  stops[0].dwell_minutes = 90  (default_dwell.palace)  ← 체류시간 미입력. 장소 유형 기본값 적용

[검사]
  ○ pass            CLOSED_DAY                 경복궁
      근거 curated https://royal.khs.go.kr/... (확인 2026-09-21, 유효 ~2026-12-31)
  ○ pass            ADMISSION_NOT_POSSIBLE     경복궁
      근거 curated https://royal.khs.go.kr/... (확인 2026-09-21, 유효 ~2026-12-31)
  ? unknown         DWELL_NOT_COMPLETABLE      경복궁
      → [NO_USER_DWELL] 체류시간을 사용자가 말하지 않았다. 기본값으로 메워서 판정하지 않는다
      해결(user) 경복궁에서 얼마나 머무르실 예정인가요?
  – not_applicable  INSUFFICIENT_TRAVEL_TIME   경복궁 → (없음)
      → 마지막 스톱이라 다음 구간이 없다

[판정]  undetermined
  pass 2 / fail 0 / unknown 1 / n.a. 1
```

휴무일도 입장도 통과했는데 전체 판정은 `feasible`이 아니다.
체류시간을 사용자가 말하지 않았으니 우리가 정한 90분으로 메워서 판정하지 않는다.
대신 `unknown`을 내고 **사용자에게 무엇을 물어야 하는지**까지 같이 낸다.

### `infeasible` — 확보한 근거에서 위반이 확인됐다

```bash
python core/run.py --case T15
```

```
입력: 10월 9일 금요일 저녁 6시 반에 서울시립미술관 서소문본관 갈게요. 한 시간 볼 거예요.

[추출]
  18:30  서울시립미술관 서소문본관  체류 60분 (사용자)

[적용한 기본값]
  없음 — 사용자가 다 말했다

[검사]
  ○ pass            CLOSED_DAY                 서울시립미술관 서소문본관
      근거 curated https://sema.seoul.go.kr/... (확인 2026-09-21, 유효 ~2026-12-31)
  ✕ fail            ADMISSION_NOT_POSSIBLE     서울시립미술관 서소문본관
      → 입장마감(18:00) 이후 도착
      근거 curated https://sema.seoul.go.kr/... (확인 2026-09-21, 유효 ~2026-12-31)
  – not_applicable  DWELL_NOT_COMPLETABLE      서울시립미술관 서소문본관
      → 입장 여부가 확정되지 않아 체류 검사가 성립하지 않는다

[판정]  infeasible
  pass 1 / fail 1 / unknown 0 / n.a. 2
```

10월 9일 한글날은 **금요일이지만 공휴일이다.** 이 미술관은 금요일 21시까지지만 공휴일은
19시까지고 입장마감이 18:00이다. 요일만 보고 시간표를 고르면 18:30 입장을 통과시킨다.

### `feasible` — 필요한 검사가 모두 통과했다

```bash
python core/run.py --case T10
```

```
입력: 10월 8일 목요일 오후 2시에 창덕궁 한 시간 반 보려고요.

[추출]
  14:00  창덕궁  체류 90분 (사용자)

[적용한 기본값]
  없음 — 사용자가 다 말했다

[검사]
  ○ pass            CLOSED_DAY                 창덕궁
      근거 curated https://royal.khs.go.kr/... (확인 2026-09-21, 유효 ~2026-12-31)
  ○ pass            ADMISSION_NOT_POSSIBLE     창덕궁
      근거 curated https://royal.khs.go.kr/... (확인 2026-09-22, 유효 ~2026-12-31)
  ○ pass            DWELL_NOT_COMPLETABLE      창덕궁
  – not_applicable  INSUFFICIENT_TRAVEL_TIME   창덕궁 → (없음)
      → 마지막 스톱이라 다음 구간이 없다

[판정]  feasible
  pass 3 / fail 0 / unknown 0 / n.a. 1
```

`feasible`은 **모든 검사에 근거가 있었을 때만** 나온다. 체류시간을 사용자가 말했고,
계절 시간표(9~10월 09:00~18:00, 입장마감 17:00)를 공식 페이지에서 확보했기 때문이다.
셋 중 하나라도 비면 위의 `undetermined`가 된다.

> 15건 전부의 입력과 출력은 `python core/run.py --all` 로 한 번에 볼 수 있다.
> 케이스 목록은 [골든 테스트](#골든-테스트)에 있다.

## 실행

**필요한 것** — Python 3.10 이상. 조회 스크립트(`.mjs`)를 돌릴 때만 Node 18 이상.

```bash
pip install -r requirements.txt     # anthropic, pydantic

# 키 없이 (판정 코어는 외부 API를 부르지 않는다)
python core/run.py                          # 골든 테스트 채점 + 실행 기록
python core/run.py --case T05               # 한 케이스 상세
python core/run.py --all                    # 전부 상세
python core/compare.py --dry-run            # 비교 실험 배선 확인
python core/compare.py --arms code          # 비교 실험, 코드 arm만
python core/build_transit_legs.py           # 지하철 주행시간 하한선 계산

# Anthropic API 키 필요
python core/run_extract.py                  # 자연어 → 추출 → 판정
python core/compare.py                      # 비교 실험 4종
python core/compare.py --model claude-sonnet-5

# 공공데이터포털 API 키 필요
python core/fetch_holidays.py 2026          # 공휴일 스냅샷 재생성

# Google Maps Platform 키 필요 (판정에는 쓰지 않는다. 능력 확인용)
GKEY=... node check-places-api.mjs
GKEY=... node check-routes-api.mjs
```

키는 그때그때 **실행 시 물어본다.** 화면에 안 찍히고 셸 히스토리에도 안 남는다.
어떤 키가 필요한지는 위 주석대로이고, 판정 코어만 돌릴 거라면 키가 아예 필요 없다.

**1. 지시를 안 하면 근거가 없어도 통과시킨다** (`llm_naive`)

`llm_naive`와 `llm_only`는 **입력이 완전히 같다.** 시스템 프롬프트만 다르고, 사실 데이터는 둘 다 받지 않았다.

```
지시 없음   보류 0.133   →  미확인 7건 중 6건을 feasible 로 냈다
지시 있음   보류 1.0     →  전부 보류. 누출 0 이지만 유효 판단도 0
```

`llm_naive`는 `facts.json`을 한 줄도 받지 않았다. 운영시간도 휴무일도 이동시간도 없다. 그런데 **정답이 `undetermined`인 7건 중 6건을 통과시켰다.** 자기 지식으로 판단한 것이다.

가장 뚜렷한 건 T14 `"2027년 3월 5일 금요일 오후 1시에 경복궁"`이다. 확보한 근거가 2026년 기준이고 `valid_until`이 `2026-12-31`이라 **2027년에는 쓸 수 없다.** `llm_naive`는 `feasible`을 냈다.

> 1차 실험에서 `llm_only`가 전부 보류한 것은 LLM의 성질이 아니라 **내 프롬프트의 결과**였다.
> 그것을 발견으로 읽지 않고 arm을 하나 더 만든 것이 맞았다.

**2. 누출 0과 쓸모를 동시에 가진 arm은 하나뿐이다**

누출이 0인 arm은 둘이다 — `llm_only`와 `code`. 그런데 `llm_only`는 **유효 판단 제공 비율이 0.0**이다. 아무 답도 하지 않으니 누출이 없는 것이다.

| arm | 누출 | 유효 판단 | |
| --- | --- | --- | --- |
| `llm_naive` | 6 | 0.867 | 많이 답하지만 근거가 없다 |
| `llm_only` | **0** | **0.0** | 안전하지만 쓸모없다 |
| `llm_with_facts` | 1 | 0.6 | |
| **`code`** | **0** | **0.533** | **틀린 확신 없이 답을 준다** |

모든 일정을 보류하면 누출은 0이 되고 사용자가 얻는 것도 0이 된다. 그 둘을 함께 봐야 하는 이유가 이 표다.

**3. 정보를 주면 크게 나아지지만 누출은 남는다** (`llm_with_facts`)

정확도 0.933으로 코드와 1건 차이다. 그 1건이 **T08 누출**이다. `"오후 4시 반에 경복궁"` — 체류시간을 말하지 않았는데 `feasible`을 냈다. `policy.json`의 `require_user_dwell_for_completion_check: true`와 그 설명을 **문서로 받고도** 적용하지 않았다.

```
arm0 → 1   지시 효과        누출 6 → 0.  단 유효 판단도 0.867 → 0.0
arm1 → 2   정보 제공 효과    정확도 0.467 → 0.933
arm2 → 3   판정 방식 효과    누출 1 → 0.  유효 판단은 0.6 → 0.533 로 양보
```

> **한계** — 15건이라 정밀도·재현율의 신뢰구간은 여전히 넓다. `정상 일정 오탐`은 분모가
> `feasible` 2건이라 사실상 정보가 없다. 반면 **누출 건수는 "있다"를 확정하는 쪽이라**
> 표본이 작아도 유효하고, 보류 비율과 유효 판단 비율은 비율로 읽을 수 있다.
>
> 7건만 채점했던 중간 결과에서는 `llm_naive`와 `code`의 보류율이 0.286으로 같게 나와
> "같은 결정성에서 코드가 더 정확하다"고 읽었는데, **15건에서는 그렇지 않다.**
> 표본이 작을 때 비율을 해석하면 이런 일이 생긴다.

## 어떻게 여기까지 왔나

지금 모양이 된 건 네 번의 수정 때문이고, **네 번 다 내가 틀린 것을 찾아서** 바뀌었다.

**1. 운영정보를 Google에서 가져올 수 없다** · 09-13

Places API는 후보 12곳 전부 `regularOpeningHours`를 반환했다. **채움률만 보면 12/12다.**
그런데 이 프로젝트의 검사가 요구하는 것으로 맞춰보면 입장마감 · 계절별 시간표 ·
공휴일 예외 규칙 · 적용기간이 **전부 없다.** 네 검사 중 셋이 성립하지 않는다.

→ 운영정보는 공식 페이지에서 사람이 확인해 넣고, Google은 `place_id`에만 쓴다.

**2. 이동시간 응답을 저장할 수 없다** · 09-21 → 09-22

Routes API로 5구간을 받아둔 뒤 약관을 확인했다. 소요시간·거리는 저장이 안 된다.
스냅샷에 넣을 수 없으면 **고정 입력으로 테스트할 수 없다.** 판정 코어를 API에서
분리한 의미가 사라진다.

→ 서울교통공사 공공누리 데이터로 교체했다. 단 이건 **열차 주행시간뿐**이라
도보·환승·대기가 빠진 하한선이다. 그래서 하한선 전용 판정 규칙을 새로 만들었다 —
하한선으로도 늦으면 `fail`, 하한선으로 도착하면 `unknown`.

**3. 첫 비교 실험 결과를 잘못 읽을 뻔했다** · 09-22

`llm_only`가 15건을 전부 보류했다. "LLM은 원래 근거 판단을 못 한다"로 읽으면
**내 결론에 유리하다.** 그렇게 쓰지 않았다.

→ LLM의 성질이 아니라 내 프롬프트가 만든 결과일 수 있다고 보고, 지시를 뺀
`llm_naive`를 arm으로 추가했다. 결과는 반대였다 — 사실 데이터를 한 줄도 안 받고도
미확인 7건 중 6건을 통과시켰다. **보류는 LLM의 성질이 아니라 지시의 효과였다.**

**4. 데이터를 고치니 정답이 바뀌었다** · 09-22

이동시간 출처를 교체하고 장소를 추가하자 15/15가 **7/15로 떨어졌다. 판정 코드는
건드리지 않았다.** 라벨 8건이 옛 데이터 상태를 전제하고 있었던 것이다.

→ 코드 출력을 보지 않고 공식 출처로만 재검토해 6건을 갱신하고 2건은 케이스 목적을
옮겼다. 이후로는 `facts.json`의 `snapshot_id`와 라벨의 `labeled_against_snapshot`을
비교해 **노후화를 자동으로 검출한다.**

> 폐기한 후보와 그 이유는 [`docs/experiments/`](docs/experiments/)에 날짜별로 있다.
> 채택한 설계만 README에 적고, 버린 것은 거기 남긴다.

## 구조

```
[조회 계층]   외부 API 호출 · 실패 처리
     ↓        fetch_holidays.py · build_transit_legs.py
     ↓        facts.json  (사실)   policy.json  (정책)
[추출]        extract.py — 자연어를 구조로 옮긴다. 값을 채우지 않는다
     ↓        LLM 이 담당하는 유일한 단계
[판정 코어]   verdict.py — 순수 함수. 네트워크 호출 없음
     ↓        checks[] + hard_constraints[] + assumptions[]
[채점·기록]   run.py · run_extract.py · compare.py → last-*.json
```

판정 코어를 외부 API에서 분리했다. **API 없이 고정 입력으로 테스트할 수 있어야** 하기 때문이다.

| --- | --- | --- |
| 자연어 → 구조화 | **LLM** | 표현이 다양해 규칙으로 못 잡는다 |
| 장소 식별 · 운영정보 · 이동시간 조회 | 코드 | |

| 실행 가능 여부 판정 | **코드** | LLM은 규칙을 일관되게 적용하지 못했다 (위 T08) |

### `core/verdict.py` — 판정 코어

| | |
| --- | --- |
| **역할** | 일정이 실행 가능한지 판정한다. 이 프로젝트의 중심 |
| **입력** | `judge(itinerary, facts, policy)` — 셋 다 **인자로** 받는다 |
| **출력** | `checks[]` · `hard_constraints[]` · `assumptions[]` · `summary` |
| **의존** | 없음. 표준 라이브러리만 쓴다 |

**네트워크를 부르지 않는 것이 규칙이다.** 이 파일에 API 호출이 한 줄 들어가는 순간 고정 입력으로 테스트할 수 없게 된다. 그래서 사실과 정책을 전부 인자로 받는다.

### `core/recheck.py` — 수정 후 전체 일정 재검사

`recheck_revision(original, revised, facts, policy)`는 수정 전과 수정 후에
각각 `judge()`를 호출한다. 바뀐 스톱만 다시 보는 것이 아니라 날짜·장소·체류시간·이동시간·필수 조건을 포함한 수정 일정 전체를 재검사하고, 변경 경로와 미해결 항목을 함께 기록한다.

**검사 종류**

| 코드 | 무엇을 보나 | 필요한 근거 |
| --- | --- | --- |
| `INPUT_REQUIRED` | **판정에 필요한 입력이 있나** | 없음. 입력만 본다 |
| `CLOSED_DAY` | 방문일이 휴무일인가 | 정기휴일 + 공휴일 캘린더 + 기관별 예외 규칙 |
| `ADMISSION_NOT_POSSIBLE` | 도착 시각에 **입장**할 수 있나 | 운영시간 + 입장마감 |
| `DWELL_NOT_COMPLETABLE` | 계획한 **체류를 마칠** 수 있나 | 위 + 체류시간 |
| `INSUFFICIENT_TRAVEL_TIME` | 다음 스톱에 제때 가나 | 구간 이동시간 + 앞 스톱 종료 시각 |

`INPUT_REQUIRED`가 나머지 넷보다 먼저 돈다. 추출 단계가 날짜나 시작 시각을 `None`으로
남기는 일이 있는데, 그 값을 시간 계산에 그대로 넘기면 프로그램이 예외로 죽는다.
**입력이 부족한 것도 검증 결과의 일부**이므로 죽지 않고 `unknown`으로 낸다.

**함수**

| 함수 | 하는 일 |
| --- | --- |
| `to_min` / `to_hhmm` | 시각을 분 단위 정수로 다룬다. 시간 계산 버그를 줄이기 위한 것 |
| `weekday_of` / `shift_date` | 요일 계산, 날짜 이동 |
| `is_last_wednesday` | '문화가 있는 날'(매달 마지막 수요일). 종묘가 이 날 일반관람으로 열린다 |
| `evidence_usable_on` | 근거의 **적용 기간** 검사. 방문일이 `valid_until`을 넘으면 그 근거는 못 쓴다 |
| `check` | 검사 결과 dict 생성. `fail`일 때만 `severity`를 붙인다 |
| `input_checks` | **판정 전에 입력이 성립하는지 본다.** 날짜·장소·시각이 비었으면 예외를 내지 않고 `unknown` 검사로 돌려준다 |
| `closed_date_for` | 그 주의 실제 휴무일 계산. **기관별 예외 규칙을 facts에서 읽어 분기** |
| `check_closed_day` | 휴무일 검사. 공휴일 캘린더가 미검증이면 `unknown` |
| `hours_for` | 그 날짜에 적용되는 시간표 선택. **공휴일 시간표가 요일보다 우선** |
| `check_admission` | 입장 가능 검사. 회차 입장·상시 개방을 각각 다른 `unknown`으로 처리 |
| `check_dwell` | 체류 완료 검사. 사용자가 체류시간을 안 말했으면 판단하지 않는다 |
| `leg_between` | `"A\|B"` 키로 구간 조회 |
| `check_travel` | 이동시간 검사. 근사값 거부, 하한선 비대칭, 기본값 민감도 검사 |
| `evaluate_hard_constraint` | KTX 같은 필수 조건. `event`(사용자)와 `policy`(우리 기준)를 분리 |
| `judge` | 본체. 기본값을 `assumptions`에 기록하고 검사를 돌려 전체 판정을 낸다 |

**`unknown_reason` 종류** — 같은 `unknown`이라도 해결 방법이 다르므로 구분한다

| 이유 | 뜻 | 어떻게 해결하나 |
| --- | --- | --- |
| `NO_CLOSED_DAY_DATA` · `NO_OPERATING_HOURS_DATA` | 정보를 못 구했다 | 데이터 확보 |
| `EVIDENCE_EXPIRED` | 근거의 적용 기간이 지났다 | 재조회 |
| `PLACE_NOT_RESOLVED` | 장소를 특정하지 못했다 | 사용자에게 물어본다 |
| `HOLIDAY_CALENDAR_UNVERIFIED` | 공휴일 캘린더가 미검증이다 | API 호출 |
| `UNVERIFIED_TRAVEL_TIME` | 구간 이동시간이 없다 | 데이터 확보 |
| `ESTIMATE_ONLY` | 직선거리 근사값뿐이다 | 실제 경로 확인 |
| `LOWER_BOUND_ONLY` | 주행시간 하한선뿐이다 | 도보·환승·대기 확보 |
| `NO_USER_DWELL` | 사용자가 체류시간을 안 말했다 | 사용자에게 물어본다 |
| `DEPENDS_ON_DEFAULT_DWELL` | 우리가 정한 기본값이 판정을 갈랐다 | 사용자에게 물어본다 |
| `BUFFER_NOT_MET` | 열차 출발 전에는 닿지만 **권장 여유에 못 미친다** | 사용자에게 알리고 판단을 맡긴다 |
| `UNSUPPORTED_ADMISSION_TYPE` | 정보는 있는데 **검사가 없다** | 코드를 고친다 |
| `UNVERIFIED_ALWAYS_OPEN` | 상시 개방 근거를 안 잡았다 | 공식 출처 확인 |

입력이 부족해서 나는 것은 따로 묶는다. 전부 사용자에게 되물어 해결한다.

| 이유 | 뜻 |
| --- | --- |
| `MISSING_DATE` · `INVALID_DATE` | 방문 날짜가 없거나 `YYYY-MM-DD`로 못 읽는다 |
| `MISSING_STOPS` · `MISSING_PLACE` | 방문할 장소가 없다 |
| `MISSING_START_TIME` | 방문 시작 시각이 없다 |
| `INCOMPLETE_HARD_CONSTRAINT` | 필수 조건에 장소 또는 시각이 빠졌다 |

> `BUFFER_NOT_MET`이 `fail`이 아니라 `unknown`인 이유 — 사용자가 반드시 지켜야 하는 것은
> **열차 출발 시각**이다. 15분 전 도착은 우리가 정한 권장 기준이지 사용자 일정의 확정
> 위반이 아니다. 출발 시각 자체를 넘기면 그때 `fail`이 된다.

**⭐ 주석이 표시한 결정** — 4상태 · 근거 적용기간 · 기관별 예외 · 공휴일 시간표 우선 · `not_applicable`도 근거 필요 · unknown 이유 구분 · 입장/체류 분리 · 근사값 거부 · 민감도 검사 · 하한선 비대칭 · 사용자 조건과 정책 분리 · status ≠ severity · **입력 결손은 예외가 아니라 `unknown`** · **구역 일정을 대표 시설로 바꿔 판정하지 않음** · 기본값 기록 · 전체 판정 · 사용자 문구

### `core/extract.py` — 자연어 → 구조화

| | |
| --- | --- |
| **역할** | 자연어 일정을 판정 코어가 읽는 구조로 **옮겨 적는다** |
| **입력** | `extract(text, client, model, today, effort)` |
| **출력** | `(Extraction, usage)` → `to_itinerary()`로 판정 코어 입력 형태로 |
| **모델** | `claude-opus-5`, structured outputs (pydantic), `effort: low` |

**LLM이 담당하는 유일한 단계다.** 판정은 시키지 않는다. 자연어를 구조로 바꾸는 데는 강하지만 규칙을 일관되게 적용하는 데는 약하기 때문이다 (비교 실험 T08 참조).

**pydantic 모델**

| 모델 | 필드 | 요점 |
| --- | --- | --- |
| `Stop` | `raw` `place` `start` `start_source` `dwell_minutes` `scope` `scope_note` | `dwell_minutes`가 **`int \| None`** 인 것이 핵심 |
| `HardConstraint` | `raw` `type` `place` `time` | `"꼭 타야 해요"` 처럼 사용자가 못 박은 조건만 |
| `Extraction` | `date` `date_source` `weekday_stated` `stops` `hard_constraints` `notes` | `weekday_stated`는 검증하지 않고 옮기기만 한다 |

`start_source`가 `explicit` / `inferred` / `missing` 셋인 이유 — `"점심 먹고"`를 12:00으로 읽은 것은 추정이고, `"오후 1시"`는 명시다. 그 구분이 없으면 나중에 무엇이 사용자 말인지 알 수 없다.

**시스템 프롬프트 규칙 7개** — 없는 값을 만들지 않는다 / 추정은 표시한다 / 장소명을 고치지 않는다 / 구역은 `area`로 남긴다 / 필수 조건은 `stops`에 중복하지 않는다 / 연도는 가장 가까운 미래로 / 요일은 옮기기만 한다

`effort: low`를 쓰는 이유 — 옮겨 적기는 기계적인 작업이라 깊게 생각할 게 없다. 출력 토큰이 절반으로 줄었는데 정확도는 같았다.

**⭐ 주석이 표시한 결정** — `int | None` · `scope: area` · LLM 경계

### `core/facts.json` — 사실

| | |
| --- | --- |
| **역할** | 판정에 쓰는 **사실**. 운영정보·이동시간·공휴일 |

| **쓰는 쪽** | 사람(curated) · `build_transit_legs.py --write` |

**최상위 구조**

| 키 | 내용 |
| --- | --- |
| `snapshot_id` | `facts-2026-09-22`. **데이터 버전.** 라벨 노후화 검출이 이걸 읽는다 |
| `snapshot_history` | 버전별로 무엇이 바뀌었는지. `changed_keys`가 노후화 판단의 근거 |
| `holidays` | `verified` · `dates[]` · 출처 · 적용기간 |
| `places` | 장소별 `closed_days` · `hours` · `admission` · `entrance` |
| `legs` | 구간별 이동시간. `"A\|B"` 키 |
| `transit_source` | 지하철 데이터 출처와 라이선스 |

**값마다 붙는 근거 필드**

| 필드 | 왜 필요한가 |
| --- | --- |
| `source` | `curated` / `public_data` / `api`. **스냅샷에 넣어도 되는 출처인지 판단하는 근거** |
| `url` · `checked_at` | 어디서 언제 확인했나 |
| `valid_until` | **언제까지 쓸 수 있나.** 이게 없으면 작년 시간표로 올해를 판정한다 |

| `rule_scope` | 그 규칙이 어디까지 적용되나 |
| `verified_by` | 확인 방법 (`공식 페이지 화면 확인` 등) |

`place.admission.type`이 `timed_entry`면 회차 입장(종묘 평일), `always_open`이면 상시 개방 후보다. 후자는 `verified: false`인 동안 `unknown`으로 나온다.

`leg`의 `is_lower_bound: true`는 **도보·환승·대기가 빠진 값**이라는 표시다. `excluded[]`에 무엇이 빠졌는지 적혀 있다.

### `core/policy.json` — 정책

| | |
| --- | --- |
| **역할** | 우리가 정한 **설정**. 기본값·버퍼·판정 기준 |
| **읽는 쪽** | `verdict.py` · `compare.py` |

**파일 첫 줄에 이렇게 적어뒀다** — `"전부 우리가 정한 값이다. 출처 URL이 없다. 사실이 아니라 설정이다."`

`facts.json`과 분리한 이유가 이것이다. 사실과 설정을 한 파일에 두면 판정 결과를 보고 "이게 공식 정보인가 우리가 정한 값인가"를 구분할 수 없다.

| 키 | 값 | 뜻 |
| --- | --- | --- |
| `default_dwell_minutes` | palace 90 · museum 60 · market_meal 60 · street 45 | 체류시간 미입력 시 쓰는 기본값 |
| `buffer_minutes.transit_leg` | 10 | 구간 이동에 두는 여유 |
| `buffer_minutes.rail_boarding` | 15 | 열차 탑승 전 권장 도착 여유 |
| `dwell_uncertainty_ratio` | 0.5 | 기본값을 **±50% 흔들어** 판정이 뒤집히면 `unknown` |
| `require_user_dwell_for_completion_check` | true | 체류시간을 안 말했으면 체류 검사를 하지 않는다 |

마지막 두 개가 "우리가 정한 값으로 사용자 일정의 오류를 만들어내지 않는다"를 구현한 것이다. 비교 실험에서 LLM은 이 정책을 **문서로 받고도** 적용하지 않았다.

[적용한 기본값]   무슨 값을 어떤 규칙으로 넣었나
[검사]           검사별 상태 · 이유 · 근거 URL · 해결 방법
[필수 조건]      사용자가 말한 것 / 서비스 권장 기준 / 계산한 예상 도착
[판정]           전체 판정과 라벨 일치 여부

| 함수 | 하는 일 |
| --- | --- |

| 표시 | 뜻 |
| --- | --- |

**채움률만 재면 12/12로 보인다.** 그래서 이 프로젝트는 운영정보를 공식 페이지 curated로 가고 Google은 `place_id`에만 쓴다.

### `check-routes-api.mjs` — Routes API 모드 확인

| | |
| --- | --- |
| **역할** | 이동수단별로 경로가 오는지 확인한다 |
| **실행** | `GKEY=... node check-routes-api.mjs` |

| 모드 | 결과 |
| --- | --- |
| `TRANSIT` | 경로 반환 |
| `WALK` | **경로 없음** (HTTP 200, 빈 결과) |
| `DRIVE` | **경로 없음** (HTTP 200, 빈 결과) |

**HTTP 200인데 결과가 비어 있다.** 이 상태를 "조회했다"로 처리하면 실패가 정상으로 바뀐다. 조회 계층에서 `시간 초과 / 응답 없음 / 필수 필드 누락`을 구분해야 하는 이유가 이것이다.

조회 스크립트는 실패를 `TIMEOUT`, `NETWORK_ERROR`, `HTTP_ERROR`,
`UNPARSEABLE_RESPONSE`, `NO_RESULT`로 기록한다. 이 값은 API에서 관찰한
상태이며, 판정 코어의 `pass`·`fail`·`unknown` 해석과 섞지 않는다.

도보 구간을 Routes API로 해결할 수 없다는 것이 여기서 확인됐다.

### `fetch-travel-times.mjs` — Routes API 이동시간 조회

| | |
| --- | --- |
| **역할** | 5구간 대중교통 이동시간 조회 + 도보 근사와 비교 |
| **실행** | `node fetch-travel-times.mjs` — 키를 터미널에서 입력받는다 |

출발 시각을 **고정한다.** 그래야 스냅샷이 결정론적이 된다. `straightMeters`로 하버사인 직선거리를 구해 우회계수 1.3, 보행속도 4km/h로 도보를 근사한다.

**관찰** — 짧은 구간에서 대중교통 경로가 도보 근사보다 오래 걸렸다. 응답을 보면 도보 → 탑승 → 도보로 쪼개져 있고 대기시간이 붙는다. 확인된 문제는 "예측이 틀렸다"가 아니라 **"구간에 맞는 이동수단을 고르지 않았다"** 다.

> **현재 판정에는 쓰지 않는다.** 응답 값(소요시간·거리)은 약관상 저장할 수 없다.
> 이동시간은 공공누리 지하철 데이터로 교체했다.

## 판정 규칙

| 규칙 | 없으면 무엇이 깨지나 |
| --- | --- |
| 근거가 없으면 `unknown` | 확인하지 않은 것을 확인했다고 말한다 |
| 근거의 적용 기간(`valid_until`)이 지나면 못 쓴다 | 작년 시간표로 올해를 판정한다 |
| 입장 가능과 체류 완료는 다른 검사 | 16:30 입장은 되지만 2시간 뒤 폐장인 경우를 통과시킨다 |
| 체류시간을 사용자가 안 말했으면 체류 검사를 안 한다 | 우리가 정한 값으로 사용자 일정의 오류를 만들어낸다 |
| 기본값을 ±50% 흔들어 판정이 뒤집히면 `unknown` | 설정값이 만든 오류를 확정 오류로 보여준다 |
| 근사값으로는 통과시키지 않는다 | 직선거리로 "충분하다"고 하고 실제로는 늦는다 |
| 하한선으로도 늦으면 `fail`, 하한선으로 도착하면 `unknown` | 빠진 값(도보·환승·대기)을 0으로 취급한다 |
| 정보가 부족해도 심각도(`severity`)를 낮추지 않는다 | KTX 문제가 "중요도 낮음"으로 보여 확인을 건너뛴다 |
| 공휴일 시간표가 요일 시간표보다 우선한다 | 한글날(금)에 금요일 시간표를 골라 통과시킨다 |
| `not_applicable`도 근거가 필요하다 | "검사 불필요"를 근거 없이 주장한다 |

## 라이선스

**저작권자가 모든 권리를 보유한다.** 이 저장소는 열람용으로 공개한 것이고,
사전 동의 없이 복제·수정·배포·2차적 저작물 작성은 할 수 없다.

포함된 제3자 데이터는 여기에 해당하지 않고 각 제공처의 조건을 따른다 —
지하철 데이터는 **공공누리 1유형(출처표시)**, 공휴일 데이터는 **이용허락범위 제한 없음**이다.
내용을 인용하거나 참조할 때 지하철 데이터의 출처 표시는 그대로 유지해야 한다.
